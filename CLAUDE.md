# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Workflow

**Every change starts as a Jira ticket in project `HE` and lands as one pull request under ~1000 changed lines.** Read `WORKFLOW.md` before starting any work — it defines the ticket model, the sizing rule, branch and commit conventions, and the Jira/GitHub automation.

The short form:
- Branch `HE-<n>-<slug>` off `master`; no long-lived integration branches.
- Commit subjects and PR titles start `HE-<n>: `. A `commit-msg` hook and the `ticket-check` CI job enforce this; Jira uses it to move the ticket to **In Review** on PR creation and **Done** on merge.
- Break a problem into tickets with `/jira-tickets <problem>` before writing code.

## Build System

HedgehogEngine uses **Premake5** to generate Visual Studio 2022 solution files. There is no CMake.

**Initial setup** (run once, or after submodule changes):
```bat
Scripts\SetupWindows.bat
```
This initializes git submodules recursively and generates `HedgehogEngine.sln`.

**Building (CLI — always build after code changes, a change is not done until it compiles):**
```
Scripts\Build.bat [Debug|Release]        (default: Debug; locates MSBuild via vswhere)
```
**Build + run all tests in one step:**
```
Scripts\RunTests.bat [Debug|Release]     (exits nonzero if the build or any test fails)
```
Alternatively invoke MSBuild directly (`MSBuild.exe HedgehogEngine.sln /p:Configuration=Debug /p:Platform=x64 /m /v:m`) or open `HedgehogEngine.sln` in Visual Studio 2022. Configurations: `Debug` and `Release`, platform: `x64`.

**Shader compilation** is automatic via a Shaders project pre-build command that calls `ThirdParty/glslc/CompileShaders.bat`, compiling `.vert`/`.frag`/`.comp` GLSL sources to SPIR-V (`.spv`).

**Build output:** every executable and DLL of a configuration goes to one directory, `Binaries/windows-x86_64/[Debug|Release]/`, so each program finds its DLLs next to it with no copy step. Static libraries and object files go to `Binaries/Intermediates/windows-x86_64/[Debug|Release]/[ProjectName]/`. The two directories are `BinariesDir` and `IntermediatesDir` in the root `Build.lua`.

**Running tests** (doctest; each exe exits nonzero on failure):
```
Binaries/windows-x86_64/Debug/HedgehogMathTest.exe
Binaries/windows-x86_64/Debug/FileSystemTest.exe
Binaries/windows-x86_64/Debug/ECSTest.exe
Binaries/windows-x86_64/Debug/EcsSerializationTest.exe
Binaries/windows-x86_64/Debug/ContentLoaderTest.exe
Binaries/windows-x86_64/Debug/HedgehogExtractTest.exe
Binaries/windows-x86_64/Debug/RenderGraphTest.exe
Binaries/windows-x86_64/Debug/HedgehogEngineTest.exe
Binaries/windows-x86_64/Debug/ScriptingTest.exe
Binaries/windows-x86_64/Debug/AnimationTest.exe
```

**Renderer smoke test** — after any renderer/RHI change, run (from the repo root, needs a Vulkan GPU):
```
Binaries\windows-x86_64\Debug\Editor.exe --smoke-test [frames]
```
Renders N frames (default 120) and exits nonzero if any Vulkan validation error occurred (Debug builds enable `VK_LAYER_KHRONOS_validation`; messages route through Logger, counters live in `RHI/api/RHIDiagnostics.hpp` and are re-exported via `Renderer.hpp`).

**Game mode** — the render-graph path as a game build runs it, with no editor:
```
Binaries\windows-x86_64\Debug\Editor.exe --game-mode [frames]
```
Loads `Assets/Scenes/Default.yaml`, builds a `Renderer` exactly as the editor does, but creates no ImGui, and renders N frames (default 120) with `RenderFrame` from views derived from the scene's camera components. Exits nonzero on any Vulkan validation error **or if an ImGui context ever exists** — the renderer not depending on ImGui is checked, not assumed. Run it after any render-graph or renderer change, alongside `--smoke-test`; like it, it needs a GPU and runs locally only.

**Regenerating solution** after modifying any `Build.lua` files:
```
Vendor\Binaries\Premake\Windows\premake5.exe --file=Build.lua vs2022
```

**CI:** `.github/workflows/ticket-check.yml` fails any PR whose title carries no `HE-<number>` key, and `module-boundaries.yml` runs `Scripts\CheckModuleBoundaries.ps1` and its `-SelfTest` (see *Architecture*). There is currently **no build workflow** — Debug/Release builds and the test exes must be run locally before opening a PR (the smoke test is local-only in any case: CI runners have no Vulkan GPU).

## Performance

- **Frame budget: 16.6 ms (60 FPS) in Release** at default window size on the baseline machine. Weigh this in any plan touching the frame loop, render passes, ECS iteration, or per-frame allocations.
- **No optimization without a before/after number.** Measure with:
  ```
  Binaries\windows-x86_64\Release\Editor.exe --benchmark [frames] [scene.yaml]
  ```
  It loads `Assets/Scenes/benchmark.yaml` (or the named file under `Assets/Scenes/`, e.g. `Default.yaml`), warms up 120 frames, measures 600, and logs CPU timings (avg/min/max/p95) for `RenderFrame(total)` and each render-graph pass (summed over the views that ran it) plus wall frame time and FPS. Always Release; run before and after the change and quote both numbers. Baseline table and methodology: `PERFORMANCE.md`.
- Per-pass rows are CPU record times (barriers plus the pass's closure, `RenderGraphRuntime::GetLastPassTimings`); GPU-bound waiting shows up in `RenderFrame(total)`, which includes the fence wait, acquire, submit and present. For GPU-side detail, connect the Tracy 0.13.1 server (client is linked in Release, `TRACY_ON_DEMAND`); zones via `HH_PROFILE_ZONE` in `HedgehogRenderer/src/Profiling/Profiler.hpp`.

## Architecture

The engine is a set of C++20 libraries (mix of static and shared) with an `Editor` executable as the entry point. Dependencies flow strictly upward:

```
Editor (ConsoleApp)            owns ImGui: context, GLFW backend, GUI renderer (RHIImGui)
  └── HedgehogEngine + HedgehogExtract + HedgehogScripting + HedgehogRenderer + RHIImGui
      + HedgehogWindow + HedgehogSettings + HedgehogCommon + DialogueWindows + ECS + FileSystem
      + Logger + Lua + imgui
        ├── HedgehogExtract  (static lib) → ECS, HedgehogEngine, HedgehogMath
        ├── HedgehogAnimation (static lib) → HedgehogMath (headers only: ContentLoader's loaded
        │                                   skin and clip structs); no caller yet
        ├── HedgehogScripting (static lib) → HedgehogEngine, ECS, HedgehogMath, FileSystem, Logger,
        │                                   Lua, sol2 (header-only); registered by the Editor
        │                                   and --game-mode
        ├── HedgehogEngine   (DLL)        → HedgehogCommon, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, HedgehogMath, ECS, EcsSerialization,
        │                                   FileSystem, yaml-cpp, Logger
        ├── HedgehogRenderer (static lib) → RHI, HedgehogMath, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, FileSystem, Logger, yaml-cpp, Tracy
        │                                   (headers only: HedgehogCommon, HedgehogExtract's
        │                                   RenderScene; never the ECS, HedgehogEngine or ImGui)
        ├── RHIImGui         (static lib) → RHI, imgui (ImGui's Vulkan renderer, via
        │                                   RHI/api/Vulkan/VulkanNative.hpp)
        ├── HedgehogWindow   (DLL)        → HedgehogMath, GLFW, Logger
        ├── HedgehogSettings (DLL)        → FileSystem, yaml-cpp, Logger
        ├── HedgehogCommon   (DLL)        → HedgehogMath
        └── RHI              (static lib) → Vulkan (Volk + VMA), Logger — no ImGui
```

`Scripts\CheckModuleBoundaries.ps1` enforces three rules on `#include` strings: no include reaches into another module's `src/`; nothing under `HedgehogRenderer/` includes `ECS/`, the engine module (`HedgehogEngine/HedgehogEngine/`, `HedgehogEngine/api/`), `imgui.h` or `imgui_impl_*`; and nothing under `HedgehogEngine/HedgehogEngine/` (tests included) includes Lua (`Lua/...`, `lua.h`, `lualib.h`, `lauxlib.h`, `lua.hpp`), sol2 (`sol/...`) or `HedgehogScripting/...`, the scripting library above it. Each include is reported once, however many patterns it matches. `-SelfTest` builds a throwaway tree shaped like the repository, plants one violation of each kind (a cross-module `src/` include, the renderer including the ECS and `imgui.h`, the engine including Lua (`ThirdParty/Lua/lua/lua.h`, `lauxlib.h`), `sol/` and `HedgehogScripting/`), checks each gives exactly one violation and that the tree passes without them (a `HedgehogScripting` module including sol2 included), and lists each case it caught. `RunTests.bat` runs the check and then the self-test before building, and CI (`module-boundaries.yml`) runs both as separate steps.

**The renderer is being rewritten.** `RENDERING.md` at the repository root is the design: a camera-and-view architecture where a `CameraComponent` carries scene data, a `View` is the render request, and each view owns a render graph. Every frame now renders through it (see *Rendering a frame* below), and the legacy fixed-pass renderer is deleted. Epic [HE-63](https://viktoravoitovych.atlassian.net/browse/HE-63) lands it as 28 sub-1000-line pull requests.

### Key Modules

| Module | Type | Role |
|--------|------|------|
| `HedgehogMath` | DLL | Vectors, matrices, AABB/OBB/Plane/Frustum primitives; `Quaternion` (identity, axis-angle and Euler in degrees, multiply, rotate, normalize, inverse, `Slerp`, `ToMatrix`, `LookRotation` turning local -Z to forward with +Y up). `FromEuler(e).ToMatrix()` equals TransformSystem's `GetRotationX * GetRotationY * GetRotationZ`, so a `TransformComponent` keeps storing Euler degrees; `ToEuler` gives y in [-90, 90] and z = 0 at gimbal lock |
| `HedgehogCommon` | DLL | Shared renderer constants (`MAX_FRAMES_IN_FLIGHT`, `MAX_LIGHTS_COUNT`, …), Camera |
| `HedgehogWindow` | DLL | GLFW window wrapper, input handling (namespace `HW`) |
| `HedgehogSettings` | DLL | YAML-based engine configuration |
| `HedgehogEngine` | DLL | Engine context; resource catalog (Material, Mesh, Texture containers); ECS systems and components; scenes (`SceneManager`: file load/save, and `CaptureSnapshot`/`RestoreSnapshot`, an in-memory `SceneSnapshot` of the YAML, scene name and game-object index; restore replaces the whole tree, brings entities back under their captured ids and runs the same post-load refresh as `LoadScene`). `Time/FixedStepClock`: a plain-data fixed-step clock (`FixedDeltaTime` 1/60, `MaxSubsteps` 8, `TimeScale`, plus accumulator, simulated `Time` and counters) with free functions `AdvanceFixedStepClock(clock, realDt)`, which returns the steps to run this frame (capped at `MaxSubsteps`, excess dropped; bad frame times count as zero; a small tolerance makes 1/30 s exactly two 1/60 s steps; bad settings fall back to the defaults), and `ResetFixedStepClock`, which keeps the settings. It has no pause flag: play mode simply stops advancing it. **Play mode** lives in `EngineContext` (`PlayState` Edit/Playing/Paused, the snapshot and the clock; the ECS only forwards events). `Play()` (from Edit) captures a snapshot, resets the clock and sends `NotifyPlayStart`; `Pause()`/`Resume()` send `NotifyPlayPause`/`NotifyPlayResume`; `Stop()` (from Playing or Paused) sends `NotifyPlayStop` (reverse order), then restores the snapshot; a call in the wrong state returns false and sends nothing. `UpdatePlayMode(dt)` (public, so tests drive frames headless) runs only while Playing: the clock's fixed steps of `RunFixedUpdate(FixedDeltaTime)`, then one `RunUpdate(dt * TimeScale)`. `UpdateContext` calls it before Transform, Hierarchy and Light, which run in every mode. `~EngineContext` sends `NotifyPlayStop` if still playing, without restoring. Scripts run in HedgehogScripting's `ScriptSystem`, which the application registers; the engine only stores `ScriptComponent` data (loading a scene runs no script code). The engine has no Lua of its own: it neither links nor includes Lua, and `ScriptComponent` is a pure-data struct (`Enable`, `ScriptPath`, `Properties`, an ordered `std::vector<ScriptProperty>`, and `Visit`). A `ScriptProperty` is `Name`, `ScriptPropertyType Type` (Number, Bool, Vector3, Color, String, EntityRef, AssetRef), `ScriptPropertyValue Value` (`std::variant<bool, float, HM::Vector3, std::string, ECS::Entity>`; Color is an RGB `Vector3`, AssetRef a path under `assets://`) and `AssetType` (the content type an AssetRef takes); free functions `FindScriptProperty` and `SetScriptProperty` find one by name and replace-or-append. Its YAML is the exported free function `RegisterScriptComponentSerializer(ComponentSerializerRegistry&)` (`api/Scene/ScriptComponentSerializer.hpp`), which `EngineContext` calls: it writes `ScriptProperties: { <name>: { Type: <type name>, Value: ..., AssetType (AssetRef only) } }` in order (an EntityRef as the entity id, which scene loads keep), and reads that or the legacy `ScriptParams` (`ParamType` 0 Boolean, 1 Number, value in `ParamValue`; the shipped Default.yaml stays in that format as the fixture); with both keys `ScriptProperties` wins and one warning is logged, and a property it cannot read (unknown type, wrong value) is skipped with a warning |
| `RHI` | static lib | Graphics abstraction: `IRHIDevice`, `IRHICommandList`, `IRHITexture`, … — dynamic rendering and `Barrier()` only (no render-pass/framebuffer objects); Vulkan backend under `src/Vulkan/`, native handles for integrations in `api/Vulkan/VulkanNative.hpp` |
| `RHIImGui` | static lib | ImGui's GPU renderer on the RHI (`RHIImGui::IGuiRenderer`), used only by the Editor |
| `HedgehogRenderer` | static lib | Multi-pass Vulkan renderer (see structure and passes below) |
| `ECS` | DLL | Entity Component System (EntityManager, ComponentManager, SystemManager, Coordinator). `ECS::System` has a virtual destructor and six play-mode events, each a no-op unless overridden: `OnPlayStart(ECS&)`, `OnPlayPause(ECS&)`, `OnPlayResume(ECS&)`, `OnPlayStop(ECS&)`, `OnFixedUpdate(ECS&, fixedDt)` and `OnUpdate(ECS&, dt)`; a system's own per-frame methods (Transform, Hierarchy, …) are separate and run in every mode. The ECS only forwards the events: `NotifyPlayStart`, `NotifyPlayPause`, `NotifyPlayResume`, `RunFixedUpdate(dt)` and `RunUpdate(dt)` visit every system in registration order, and `NotifyPlayStop` in reverse. The ECS keeps no play state and checks nothing; whoever drives play mode (the engine) owns the state, the clock and the scene snapshot, and decides when each event is due. `RegisterSystem<T>(args...)` forwards constructor arguments, systems keep registration order (`SystemManager::ForEachSystem`/`ForEachSystemReverse`), and `~ECS` destroys systems before component storage, so a system may clear its removal callback from its destructor; the ECS is movable, not copyable. `SetComponentRemovedCallback<T>(fn(Entity, T&))`: one callback per component type (a new one replaces the old, an empty one clears it; `GetComponentRemovedCallback<T>()` returns the current one, so a system can chain it and put it back), fired before the data goes, from `RemoveComponent<T>` and from `DestroyEntity`; `DestroyEntity` runs every array's callback before removing any component and releases the id last, so a callback sees all of the entity's components and `IsAlive` is still true. Entity generations: `IsAlive(e)` and `GetGeneration(e)`, bumped on destroy so a stale id+generation pair is detectable; destroying twice asserts. `SetSystemSignature<T>` backfills live entities that already match |
| `EcsSerialization` | DLL | ECS serialization; `IHierarchyProvider` interface decoupled from engine |
| `HedgehogScripting` | static lib | The scripting library above the engine (namespace `HedgehogScripting`, ADR-022); links HedgehogEngine, ECS, HedgehogMath, FileSystem, Logger and Lua, and the Editor (`Application::Init`, right after the Engine, before EditorGui loads the last scene) and `--game-mode` (before its scene load) register it; the ECS owns it, and `EditorGui` keeps a non-owning pointer (`SetScriptSystem`). **`ScriptSystem : ECS::System`** (`api/ScriptSystem.hpp`), signature `ScriptComponent` + `TransformComponent`, built only by the free function `RegisterScriptSystem(EngineContext&, const FS::FileSystemManager& scriptFiles)` (registers it in the engine's ECS and sets the signature; `scriptFiles` resolves `assets://` and must outlive it; the constructor takes the `EngineContext&` too, for the ECS and EventBus the Entity API uses). It reads `ScriptComponent` (`Enable`, `ScriptPath`, normalized by `NormalizeScriptPath`: `Scripts\X.lua` → `assets://Scripts/X.lua`) and owns all runtime state as private members: one sandboxed `sol::state`, the class-support functions, `m_Classes` (private nested `ScriptClass`: a file's defaults and class table, keyed by path) and `m_Scripts` (private nested `EntityScript`: path, generation, entity name, environment, `self`, started/faulted, keyed by entity). The base `Scripts/Base/ActorScript.lua` runs once in a base environment; each script file compiles once per Play (`m_Classes` is cleared in `OnPlayStart`, so edits are re-read) under a proxy `_ENV` into a fresh defaults table, and its class is the global named by the file stem. Each entity's environment is a shallow copy of the defaults falling back to the base environment, so top-level globals are per entity while methods are shared; `self` is `Class:new()` and every call goes through `invoke(env, self, method, ...)`. Events: `OnPlayStart` makes an instance for every entity with a script path (enabled or not), with its property values on `self` (see declared properties below), and chains a `ScriptComponent` removal callback in front of the engine's own (read with `GetComponentRemovedCallback`, put back at `OnPlayStop` or in the destructor). `OnFixedUpdate(fixedDt)` and `OnUpdate(dt)` each start with `SyncScripts`: an entity that gained a script during Play gets an instance, one that left the system (lost its Transform, died, or was recycled) gets OnDisable and OnDestroy, and `Enable` compared with the system's own `EntityScript::Enabled` gives OnStart (once, on the first enable), OnEnable and OnDisable; then every enabled script gets `OnFixedUpdate(fixedDt)` or `OnUpdate(dt)`, entities in id order. So a first 1/30 s frame at 1/60 runs OnStart, OnEnable, OnFixedUpdate twice, OnUpdate. Removing the component or destroying the entity (`RemoveComponent`, `DestroyEntity`, `DeleteGameObject`) during Play gives OnDisable (if enabled) and exactly one OnDestroy; a removal while that entity's own call runs is deferred until the call returns. `OnPlayStop` gives every script OnDisable and OnDestroy, before the engine restores the scene. A script error is logged once as `[Script] <entity name> (<assets://path>): <message>` with a traceback; an error in OnStart, OnEnable, OnFixedUpdate or OnUpdate, or a script that fails to load, faults it: skipped (not retried) until the next Play, OnDestroy still attempted, the others carry on. Declared properties (`src/ScriptSystemProperties.cpp`, `ScriptSystem` members): a script declares what the inspector shows in a top-level `Properties` table, in a short form (`speed = 1.0`, `clockWise = true`, `label = "x"`, `offset = Vector3(0, 1, 0)`, `tint = Color(1, 0, 0)`, `target = EntityRef()`, `mesh = AssetRef("Mesh"[, path])`) or a long form (`{ type = "number"|"bool"|"vector3"|"color"|"string"|"entity"|"asset", default = ..., min = ..., max = ..., tooltip = "...", assetType = "..." }`; the type may be left out when a default gives it; `Color` (default white), `EntityRef` and `AssetRef` are globals returning the long form). Each compile reads them into its `ScriptClass` as `ScriptPropertyDeclaration`s (`api/ScriptPropertyDeclaration.hpp`, pure data: the default `ScriptProperty`, optional `Min`/`Max` for numbers, `Tooltip`), listed by name since a Lua table has no order; an entry it cannot read (unknown type, a default of the wrong type, a function, no type and no default) is skipped with a warning `[Script] <path>: property '<name>' is skipped: <why>.`. Right after `new()` each declared property is set on `self.<name>`: the component's saved value when its name and type match, else the default (a saved value of another type gives the default and one warning `[Script] <entity> (<path>): property '<name>' is saved as <type> but declared as <type>`; a saved value no longer declared stays in the component, unused, with one warning). Number and Bool become Lua numbers and booleans, Vector3 and Color a `Vector3`, String and AssetRef strings, an EntityRef an `Entity` handle (invalid when the id is unset or the entity gone). Top-level globals are no longer properties. `PushProperties(ecs, entity)` re-applies the component's values to `self` for live inspector edits, without the warnings (nothing outside Play); `DescribeScript(path)` compiles a throwaway class and returns its declarations, running no method and logging nothing on success. `GetScriptCount`, `GetCompileCount` and `GetRunningEntity` expose its state. Its constructor registers the script globals from `src/Bindings/` (free functions `Bindings::RegisterMath` and `Bindings::RegisterLog`): `Vector3` over `HM::Vector3` (`Vector3()`/`Vector3(x, y, z)`, read-write `x`/`y`/`z`, `+ - * /` with a Vector3 or a number, unary minus, `==`, `dot`, `cross`, `length`, `normalized` (zero stays zero), `lerp`, `tostring`) and `Quat` over `HM::Quaternion` (`Quat()`/`Quat(x, y, z, w)`, `Quat.identity`, `fromEuler` (three numbers or a Vector3, degrees), `axisAngle`, `lookRotation`, `slerp`, `q:euler()`, `inverse`, `normalized`, read-only `x`/`y`/`z`/`w`, `*` with a Quat or a Vector3, `==`, `tostring`); and `Log.info`/`Log.warn`/`Log.error`, each one Logger line `[Script] <chunk>:<line>: <args>` (arguments through `tostring`, joined by spaces; a failing `__tostring` is a script error that logs nothing), with `print` replaced by `Log.info`. A wrong argument (`Vector3(1, 2, 3) + 5`) is a script error in Debug and Release. `Bindings::RegisterEntity` adds the Entity API over pure-data handles (`src/Bindings/ScriptHandles.hpp`): `ScriptEntity { Id, Generation }`, valid while `IsAlive(Id)` and the generation still matches, and `ScriptComponentRef<T> { ScriptEntity }`, which looks its component up on every access and never keeps a pointer into component storage. Every script's `self.entity` is its own entity's handle, set right after `new()`. `Entity`: `id`, `isValid()`, `name` (get and set, through `HierarchyComponent`), `parent` (nil at the top level), `children` (a new array, hierarchy order), `transform`, `==`, `tostring` (`Entity <id> (generation <g>)`). `Transform` (`ScriptComponentRef<TransformComponent>`): `position`, `eulerAngles` (degrees, as stored), `rotation` (a Quat; writes store its Euler angles), `scale`, `forward`/`right`/`up` (unit world axes from the last computed `ObjMatrix`, -Z forward), `translate(v)`, `rotate(eulerDegrees | x, y, z | Quat)`; every write publishes `TransformChangedEvent`, so Transform and Hierarchy, which run after `UpdatePlayMode`, apply it the same frame. Using a stale handle raises a script error naming the id and generation. `Bindings::RegisterComponents` (`src/Bindings/ComponentBindings.cpp`) adds `Light`, `Camera` and `Mesh` over `ScriptComponentRef<T>`, reached by `entity:getLight()`/`getCamera()`/`getMesh()` (nil when absent), `hasX()` and `addX()` (adds a default one as the editor's Add Component menu does, a new light marking its transform changed and a new mesh getting the default cube through `MeshSystem::Update`; an existing one is returned as is). Fields mirror the reflected ones and write straight to the ECS: Light `enabled`, `type`, `color`, `intensity`, `radius`, `coneAngle`, `castShadows` (through `LightSystem::SetShadowCasting`, so one light casts); Camera `enabled`, `projection`, `fov`, `orthoSize`, `near`, `far`, `layerMask` (0 to 0xFFFFFFFF), `targetMode`, `targetName`, `graphName`, `priority`; Mesh `path` (under `assets://`, prefix optional; setting it loads the mesh with `MeshSystem::LoadMesh`, and a path with no file is a script error). Enums are integers named by the global tables `LightType` (Directional, Point, Spot), `CameraProjectionType` and `CameraTargetMode`; a value outside one is a script error. A handle whose component is gone raises `Entity <id> (generation <g>) has no <T::s_TypeName>`. Both `RegisterEntity` and `RegisterComponents` take the `EngineContext`; components added during Play go at Stop's restore. `Bindings::RegisterScene` (`src/Bindings/SceneBindings.cpp`) adds the `Scene` table over the context's `SceneManager`: `Scene.find(name)` (the first game object with that name in depth-first hierarchy order, or an invalid handle), `Scene.findAll(name)` (every match, same order), `Scene.spawn([name], [parent])` (`SceneManager::CreateGameObject`, so Transform, Hierarchy and a unique name unless one is given, under parent or the root) and `Scene.destroy(e)`/`entity:destroy()`. Destroying only queues the handle in the system's `m_PendingDestroys` (a stale or already queued handle logs one warning and does nothing); `Bindings::FlushDestroys` runs at the end of `OnFixedUpdate` and `OnUpdate`, after every script in the hook, and deletes each still-valid one with `SceneManager::DeleteGameObject` (children move up to the grandparent), so a destroyed scripted entity gets OnDestroy through the removal callback after the others' calls. Spawned entities go at Stop's restore. Script events (`src/ScriptSystemEvents.cpp`, `ScriptSystem` members, since the engine's `EventBus` is typed per C++ struct and cannot unsubscribe): `Events.subscribe(name, fn)` returns an id and belongs to the entity whose script is running (outside a script method it is a script error), `Events.unsubscribe(id)` returns whether it removed one, and `Events.publish(name, payload?)` queues the event (private nested pure-data `EventSubscription` and `QueuedEvent`, kept in `m_Subscriptions` by name and `m_QueuedEvents`). `OnUpdate` dispatches the queue after every script's OnUpdate, so no handler runs inside another script's call; each handler runs as `fn(payload, name)` in its owner's environment through the class support's `run`, with the payload table passed as is; an event published during dispatch waits for the next frame, so a handler that republishes cannot loop; a handler error is logged as `[Script] <entity> (<path>): handler for event '<name>': ...` and neither faults the script nor stops the other handlers. An owner's subscriptions go with its script (`DestroyScript`), and all of them at Play start and Stop; a faulted owner's handlers are skipped. `GetSubscriptionCount()` counts them. `Bindings::RegisterTime` (`src/Bindings/TimeBindings.cpp`) adds the `Time` table, read through a metatable so every read is current: `Time.deltaTime` (the hook's dt: OnUpdate's scaled dt, the fixed dt inside OnFixedUpdate), `Time.fixedDeltaTime` and `Time.time` (the engine's `FixedStepClock`: its step and its scaled simulated time), `Time.frame` (OnUpdate calls since Play, counting the current one) and `Time.timeScale`, the only writable field, clamped to [0, 100] (a non-number or non-finite value is a script error) and stored in the clock through `EngineContext::GetFixedStepClock`, so it applies from the next frame's steps (the current frame's were counted before scripts ran). The dt and frame are `ScriptSystem` members (`m_DeltaTime`, `m_Frame`), reset at Play start; the clock resets on Play itself. The fixed step stays the clock's default (1/60 s, 8 substeps); engine_settings.yaml does not set it. Coroutines (`src/ScriptSystemCoroutines.cpp`, `ScriptSystem` members): `startCoroutine(fn)` returns an id owned by the running script (outside a script method it is a script error), `stopCoroutine(id)` returns whether it ended one (a coroutine may stop itself and is never resumed again), and inside one `wait(seconds)`, `waitFrames(n)` and `waitUntil(predicate)` suspend it (a plain `coroutine.yield()` waits one frame; calling one outside a `startCoroutine` coroutine is a script error at the caller's line). Each is a Lua thread of the one state, kept in its `EntityScript` as a private nested pure-data `ScriptCoroutine` (id, thread, wake kind, wake time, frames left, predicate). `OnUpdate` resumes the due ones after every script's OnUpdate and before the events are dispatched, entities in id order and then start order; a new one first runs in that pass (the next frame's when a coroutine or handler starts it), always in its owner's environment. `wait` counts `m_CoroutineTime`, the scaled dt OnUpdate has passed since Play, so Pause freezes it and `Time.timeScale` scales it; `waitFrames(n)` resumes n OnUpdates later (at least one); `waitUntil` checks its predicate each pass and resumes on the first true. A disabled or faulted script's coroutines hold where they are. An error in a coroutine or predicate is logged as `[Script] <entity> (<path>): coroutine: ...` with the coroutine's traceback and ends only that coroutine; coroutines die with their script (destroy, component removal, Stop). `GetCoroutineCount()` counts them. Hot reload (`src/ScriptSystemReload.cpp`, `ScriptSystem` members): `ReloadChangedScripts(ecs, now = steady_clock::now())`, which the Editor calls every frame from `Application::StepFrame` (`--game-mode` does not), polls at most once per `RELOAD_POLL_INTERVAL` (1 s; `now` is a parameter so tests need not wait) and compares each compiled class's file write time (`ScriptClass::PhysicalPath`/`WriteTime`, found with `ResolvePhysical` and `std::filesystem::last_write_time`, since FileSystem has no write-time query) with the one it was compiled from. A changed class no running script uses is dropped (compiled afresh when next needed, so in Edit mode nothing is recompiled). One with running scripts is compiled again (`CompileClass`, which `FindOrCompile` also uses) and each of its scripts swapped: a new environment from the new defaults and a new `self` from `new()`, the old `self`'s state copied by a Lua `copyState` (every entry but `entity`; numbers, booleans, strings and userdata such as `Vector3`, `Quat` and handles as they are, tables deeply with each table copied once so cycles stay cycles, metatables kept, functions and threads dropped), the properties applied again (no warnings), coroutines stopped, `Faulted` cleared, then `OnReload()` if the class has one; OnStart does not run again, top-level globals start from the new file, event subscriptions are kept, and a script that never loaded is created afresh. A file that no longer compiles keeps the old class running and logs its error once (that version is not retried; the next save is), and a reload logs `[Script] Reloaded <path> for <n> entities.`. The legacy `GetPosition`/`SetPosition`/`GetRotation`/`SetRotation` globals are not provided: the shipped `PlayerScript.lua` turns through `self.entity.transform.eulerAngles` and declares `Properties` (`speed`, long form with a tooltip, and `clockWise`), read as `self.speed` and `self.clockWise`, so Default.yaml's saved values (still in the legacy format) apply, and `ActorScript.lua` logs with `Log.info`. ### HedgehogRenderer Structure

The renderer follows a strict `api` / `src` split:

```
HedgehogRenderer/
├── api/
│   └── HedgehogRenderer/
│       └── Renderer.hpp          ← sole public header
└── src/
    ├── Renderer/Renderer.cpp
    ├── RHIContext/               ← owns IRHIDevice + IRHISwapchain
    ├── Renderer/FrameRenderer    ← the frame: per-frame command lists, fences and semaphores,
    │                               views, shared phase, per-view graphs, present
    ├── Graph/                    ← the render graph, graph assets, engine pass types
    │   └── Passes/               ← one .hpp/.cpp per engine pass type, plus PassCommon
    ├── GraphPasses/              ← GraphPassServices: pipelines and uniform rings for the passes
    ├── Views/, Targets/, Frame/  ← ViewManager and culling, RenderTargetRegistry, SharedPhase
    ├── ResourceRegistry/         ← mesh/material GPU buffers and descriptor sets
    └── Pipeline/, Profiling/     ← .shader/.pl loading; FrameStats and Tracy zones
```

`api/` is the public include root (added to dependents' include paths).  
`src/` is private — never included from outside the module.

### Rendering a frame (HedgehogRenderer)

Every frame goes through the render graph: the Editor (and `--game-mode`) builds a `Renderer`, simulates, extracts a `RenderScene`, calls `SyncResources`, then `Renderer::RenderFrame`, which owns the frame lifecycle inline (fence wait, resize before acquire, shared phase, per-view graphs, one execute, present) in `src/Renderer/FrameRenderer`. The editor has three views (RENDERING.md section 7): **scene** (the flycam into the `scene` target), **game** (the scene's camera, redirected to the `game` target with `SetCameraTargetOverride`), and **result** (no camera; the `result` graph's `Ui` pass draws the editor into `main`, sampling both panel targets). A hidden panel tab is sized 0x0, so its view is dropped and its passes never declared (`GetLastFramePassCount`).

Graph passes (`assets/Graphs/*.graph`; each pass type is one `.hpp`/`.cpp` pair in `src/Graph/Passes/` exposing `Get<Name>PassType()`, its slots, parameters and build function, and `EnginePassTypes` registers them): the shared phase's **Shadow** (the cascaded shadow atlas, once per frame), then per view **DepthPrepass** → **Forward** (lit, samples the atlas) → **Gizmo** (scene view only: editor-layer bounds), and the result view's **Ui** (the application's `UiCallback` into `main`). Views are culled by layer mask and frustum.

The legacy fixed-pass renderer is gone: `DrawFrame`, every legacy pass, `RenderQueue` and `ResourceManager` with its textures. Render order comes from the graph compiler's topological sort, render targets are either pooled graph transients or view-owned targets in the render-target registry, the `Renderer` owns the mesh/material `ResourceRegistry` directly, and `FrameRenderer` owns the per-frame command lists and synchronization objects. `Renderer.hpp`'s public surface is `RenderFrame`, `SyncResources`, `Cleanup`, the frame-stats pair and the view accessors (`CreateView`/`UpdateView`/`DestroyView`, `SetCameraTargetOverride`, `DeclareTarget`/`ResizeTarget`/`GetTargetTexture`, `GetLastFramePassCount`) and, for tools, the graph assets and pass types (`GetGraphNames`, `FindGraphAsset`, `GetGraphFile`, `FindPassType`, `GetPassTypeNames`, `GetGraphError`, `DiagnoseGraph`). The Editor's render graph editor (`Editor/Tools/RenderGraphEditor/`) draws and edits a graph with them: its edits are plain `GraphAsset` operations in `GraphEditing`, it checks every edit with `DiagnoseGraph` (problems in red on their node, and in a list under the canvas), it saves through `GraphAssetWriter` and the renderer hot-reloads the file, and node positions live in a `<name>.graph.layout` file beside the graph. New starts an empty untitled graph, Open... and Save As... pick any `.graph` file (`DialogueWindows::RenderGraphOpenDialogue`/`RenderGraphSaveDialogue`), and a picked file is named by `MakeGraphReference` (`Tools/RenderGraphEditor/GraphFileReference`): an engine graph's name, else a virtual path under the most specific mount, else an absolute path, normalized as the renderer lists it, and registered with `Renderer::LoadGraph`. The camera inspector (`EditorGui::DrawCameraGraph`) names the same references: its drop-down shows engine graphs by name and files by file name, Browse... picks a file through the same dialogue and `MakeGraphReference`, Edit opens the camera's graph with `RenderGraphEditorWindow::OpenGraph`, and a reference with no usable graph shows in red with the renderer's reason.

**ImGui belongs to the Editor, never the renderer.** `Editor/ImGuiLayer` owns the context, the GLFW platform backend and the GUI renderer (`RHIImGui::IGuiRenderer`, ImGui's Vulkan backend with dynamic rendering into any texture of one colour format, created in the `Renderer`'s `DeviceReadyCallback`, which hands the application the device and the swapchain's format once at construction). The result view's `Ui` pass hands the editor its colour target through a `UiCallback`. Neither `HedgehogRenderer` nor `RHI` has an ImGui include path or link, and the boundary check keeps it that way.

### Project Configuration Files

Each module has its own `Build-[ModuleName].lua` file included from the root `Build.lua`. Global third-party paths and library names are centralized in `Dependencies.lua`. Modifying either requires regenerating the solution.

(`PassBuilderRegistry`/`PassInvocation`/`GraphInstantiator` — semantic validation naming pass and slot, the view output contract, outputs written into caller-supplied target textures, and the **C++ equivalence oracle**: `GraphPlanOracle.hpp` renders a compiled plan as name-keyed text so an asset-instantiated graph and its hand-written twin must compile identically), and the shipped graphs (`assets/Graphs/scene|game|result.graph` against `RegisterEnginePassTypes`, each with a hand-written twin, plus `GraphAssetLibrary` hot reload and last-known-good fallback on a broken edit, and directory registration: every `*.graph` under its stem, sorted names, files added later picked up by `Poll()`, and graph references (`GraphReference` — a view's `GraphName` is a registered name or a `.graph` file by virtual or absolute path, normalized so every spelling of one file registers once) loaded by `FindOrLoad` on first use, hot-reloaded like the rest, a missing file reported and picked up once it exists), and the render-target registry (`Targets/RenderTargetRegistry` — `main` and declared targets, all three size policies across a swapchain resize, end-of-frame resize with fence-deferred destruction, zero-area reporting), and views (`Views/ViewManager` — derivation from `RenderScene` cameras with stable ids, application views untouched by reconciliation, target overrides that leave the source camera byte-identical, build-time drops, derived views never including the editor layer), and per-view culling (`Views/ViewCulling` — layer mask and frustum, editor-layer instances split out as the Gizmo pass's overlay), and view ordering (`Views/ViewOrdering` — writer-before-reader order from render-target dependencies, `Priority` only as a tie-break, cycles reported naming every view and resolved by dropping one), and engine pass recording (the `src/Graph/Passes/` depth prepass, shadow, forward and Ui execute bodies — the Ui pass runs the frame's `UiCallback` after sampling the targets its view reads, or clears without one; the Gizmo pass draws the overlay instances' bounds over the view, recording nothing without any — driven through a fake `IGraphPassServices` and the counting `RecordingCommandList`; `ShadowCascades` math; `MakeForwardViewUniform`/`MakeSceneLightsUniform` packing and std140 layout), and the shared frame phase (`Frame/SharedPhase` — the shadow atlas declared once and imported by any number of view graphs through schema-v2 `imports`, ordered and barriered by the compiler, culled when no view reads it; casters chosen by `ShadowCasterMask`, never the view's layer mask; scene lights uploaded once per frame; `SelectShadowView`). The real `GraphPassServices` (pipelines + per-frame viewProj, forward-view and scene-light uniform rings) lives in `src/GraphPasses/`, outside what the test compiles. Links `HedgehogMath` (a DLL, found next to the test in the shared output directory) for `RenderScene`. Compiles the graph's sources directly rather than linking the `HedgehogRenderer` static lib and links only `Logger` and the static `yaml-cpp` beyond that, so it needs no Vulkan SDK, GLFW, or ImGui — a fake `IRHIDevice`/`IRHICommandList` pair in `TestRHIDoubles.hpp` (zero Vulkan dependency, since those interfaces have none of their own) stands in for a real device.

Every executable and DLL builds into the one output directory (`BinariesDir`), so a new test project that links a `SharedLib` module needs nothing beyond `links`: no copy step. A new project uses `targetdir (BinariesDir)` if it is an executable or DLL, `targetdir (IntermediatesDir)` if it is a static library, and `objdir (IntermediatesDir)` either way.

Everything else in the renderer (the RHI-backed render passes) has no unit tests by design; it is covered by validation layers + `Editor.exe --smoke-test` (see Build System). The render graph's declaration layer above is the deliberate exception — it is device-free by construction (RENDERING.md section 5.3), so it is unit-tested like any other module.

### Third-Party Dependencies (git submodules)

glfw, ImGui, imgui-node-editor (the Editor's render graph canvas), yaml-cpp, tinygltf, doctest, Lua, sol2, Tracy — all under `ThirdParty/`, each pinned to a commit of a fork under `vVoitovych`. The imgui-node-editor fork carries a small patch for the ImGui version in use; update it there, not in the submodule's working tree. Lua is pinned to the `v5.4.9` release (312b9efa): the scripting epic binds it with sol2, which does not handle Lua 5.5's `lua_newstate(seed)`, so stay on the 5.4 line until sol2 supports 5.5. sol2 (header-only, `ThirdParty/sol2/sol2`) is pinned to 9190880c, the v3.5.0 release commit (the fork has no tags), and is included only through `HedgehogScripting/api/Sol.hpp`. Vulkan SDK headers/libs are also under `ThirdParty/vulkan/`.
