# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Workflow

**Every change starts as a Jira ticket in project `HE` and lands as one pull request under ~1000 changed lines.** Read `WORKFLOW.md` before starting any work — it defines the ticket model, the sizing rule, branch and commit conventions, and the Jira/GitHub automation.

The short form:
- Branch `<epic>/HE-<n>-<slug>` (e.g. `physics/HE-301-rigidbody-component`) off `master`; no long-lived integration branches.
- Commit subjects and PR titles start `HE-<n>: `. A `commit-msg` hook and the `ticket-check` CI job enforce this; Jira uses it to move the ticket to **In Review** on PR creation and **Done** on merge.
- Break a problem into tickets with `/jira-tickets <problem>` before writing code.

Every `Assets/...` path in this file is under it, and every tool run in the dev tree with no project named plays it (`FS::GetProjectRootDirectory`). The repository root holds the engine: `Engine.yaml`, `Content/`, `Templates/` and the modules. **Project templates** (since HE-299): a new project is a copy of a template the engine ships, so what it holds is data. `Templates/Empty/` (`HedgehogSettings::EMPTY_TEMPLATE_DIRECTORY`, under the engine root, never packaged) is a complete project: `Project.yaml` (startup scene `assets://Scenes/Main.yaml`, no plugins), `engine_settings.yaml`, `Assets/Input/actions.yaml` (the defaults as `WriteInputActions` writes them), `Assets/Scenes/Main.yaml` (a cube of the engine's content with `Assets/Materials/Default.material`, the cells texture, a sun and a camera) and empty `Models`, `Prefabs`, `Scripts` and `Textures` folders (kept in git by `.gitkeep` files, `FOLDER_PLACEHOLDER_NAME`, which are not copied). `HedgehogSettings/api/ProjectTemplate.hpp`: `CreateProject(templateDir, targetDir, name)` copies the template into `targetDir` (which must not exist, or be an empty folder), names it through `ProjectSettings::SetName` and saves its `Project.yaml` through a `project://` of its own; it returns an empty string, or why it failed (a name `IsValidName` refuses, a template without `Project.yaml`, a target that is not an empty folder, a copy, read or save that fails), having removed what it made (the folder it created, or the contents of the empty folder it was given).

HedgehogEngine uses **Premake5** to generate Visual Studio 2022 solution files. There is no CMake.

**Initial setup** (run once, or after submodule changes):
```bat
Scripts\SetupWindows.bat
```
This initializes git submodules recursively and generates `HedgehogEngine.sln`.

**Building (CLI — always build after code changes, a change is not done until it compiles):**
```
Scripts\Build.bat [Debug|Release]        (default: Debug; locates MSBuild via vswhere)
```
**Build + run all tests in one step:**
```
Scripts\RunTests.bat [Debug|Release]     (exits nonzero if the build or any test fails, a crashing test, whose exit code is negative, included)
```
Alternatively invoke MSBuild directly (`MSBuild.exe HedgehogEngine.sln /p:Configuration=Debug /p:Platform=x64 /m /v:m`) or open `HedgehogEngine.sln` in Visual Studio 2022. Configurations: `Debug` and `Release`, platform: `x64`.

**Shader compilation** is automatic via a Shaders project pre-build command that calls `ThirdParty/glslc/CompileShaders.bat`, compiling `.vert`/`.frag`/`.comp` GLSL sources to SPIR-V (`.spv`).

**Build output:** every executable and DLL of a configuration goes to one directory, `Binaries/windows-x86_64/[Debug|Release]/`, so each program finds its DLLs next to it with no copy step. Static libraries and object files go to `Binaries/Intermediates/windows-x86_64/[Debug|Release]/[ProjectName]/`. The two directories are `BinariesDir` and `IntermediatesDir` in the root `Build.lua`.

**Choosing the project** (since HE-297): every Editor mode takes `--project <folder or its Project.yaml>` (one without `Project.yaml` exits 1 with one error naming it). Without it, the interactive editor opens the most recent project in the per-user recent list that still exists, else the default (`Projects/FeatureTest` in the dev tree); `--smoke-test`, `--game-mode` and `--benchmark` never read the recent list, so they stay reproducible. `Editor::SelectStartupProject` (`Application.hpp`) chooses through the ImGui-free `Project/StartupProject` (`IsProjectFolder`, `ChooseStartupProject(argument, recent, defaultProject) -> StartupProjectChoice { Path, Error }`) and calls `FS::SetProjectRootDirectory` before the engine is built. Only the interactive editor records its project as the most recent (`EditorApplication(windowMode, recordRecentProject)`, `EditorGui(context, recordRecentProject)`); the window title is `HedgehogEngine - <project name>`. A scene argument may come anywhere after its flag (`--game-mode 60 --project Game Hud.yaml`). **Switching projects** (since HE-298): File > Open Project... (a folder, `DialogueWindows::ProjectOpenDialogue`; since HE-340 the folder dialogs, New Project's and Build Game's Browse... too, are Windows' `IFileOpenDialog` with `FOS_PICKFOLDERS` on a thread of their own in a single-threaded COM apartment, without an owner window, since tinyfd's `SHBrowseForFolder` never showed on the main thread, whose apartment the audio engine makes multithreaded, and froze the editor; and `ConfirmProjectSwitch`'s message holds no quote, which tinyfd refuses) and File > Recent Projects (every entry with its path; the open one checked, one whose folder is gone shown `(missing)` and disabled, and Remove Missing Projects clearing those; missing entries are no longer dropped at start), both in Edit mode only, go through `EditorGui::RequestProject`: a folder without a readable `Project.yaml` is one Console error and nothing more, else `DialogueWindows::ConfirmProjectSwitch` asks (unsaved scene changes are lost), the project goes first in the recent list and `TakeProjectRequest()` hands it to `EditorApplication::MainLoop`, which ends the run. `Run` returns `RunResult { RequestedProject }`, the editor is torn down exactly as on exit, and `main.cpp`'s loop sets the project root and builds a new `EditorApplication` on it in the same process (the window closes and reopens; a relaunch would detach a debugger). A project's last scene, else its startup scene, opens with it. **New Project** (since HE-300): File > New Project... (Edit mode only) opens `Tools/NewProjectWindow`: a name, a parent folder (Browse..., `DialogueWindows::ProjectFolderDialogue`; by default the open project's parent) and the folder it makes, `<parent>/<name>` (`MakeNewProjectFolder`). Create is disabled, with the reason shown, while the ImGui-free `Tools/NewProjectCheck`'s `CheckNewProject(name, parent)` refuses (a name `ProjectSettings::IsValidName` refuses, a parent that does not exist, a folder that exists and is not empty); it calls `HedgehogSettings::CreateProject` with the engine's `Templates/Empty`, shows its reason on failure, and on success opens the new project through `RequestProject(folder, confirm = false)` (the window already says unsaved scene changes are lost), so it comes first in Recent Projects and opens on the template's `Main.yaml`. `--smoke-test [frames] --switch-project <folder>` exercises the same rebuild: the editor on its project, then rebuilt on the other and back three times in one process, every validation error counted (a folder without `Project.yaml` exits 1).

Renders N frames (default 120) and exits nonzero if any Vulkan validation error occurred (Debug builds enable `VK_LAYER_KHRONOS_validation`; messages route through Logger, counters live in `RHI/api/RHIDiagnostics.hpp` and are re-exported via `Renderer.hpp`).

**Game mode** — the render-graph path as a game build runs it, with no editor (a thin caller of HedgehogRuntime's `GameRuntime`, the game loop itself):
```
Binaries\windows-x86_64\Debug\Editor.exe --game-mode [frames] [scene.yaml]
```
Loads the named file under `Assets/Scenes/`, else the project's startup scene (`Project.yaml`'s `startup_scene`), else `Assets/Scenes/Default.yaml` (named files, e.g. `Animated.yaml`, two animated `TwoBoneStrip`s and a rigid cube, for skinned rendering, or `Spinner.yaml`, a cube the Spinner sample plugin turns beside a still one, or `Physics.yaml`, the physics sample, or `Hud.yaml`, a cube under a game UI canvas: a translucent top bar with a logo and a title, a health bar with its value and a tinted textured button labelled PLAY, the text in `Content/Fonts/Karla-Regular.ttf`, SIL OFL 1.1), builds a `Renderer` exactly as the editor does, but creates no ImGui, and renders N frames (default 120) with `RenderFrame` from views derived from the scene's camera components. Exits nonzero on any Vulkan validation error **or if an ImGui context ever exists** — the renderer not depending on ImGui is checked, not assumed. Run it after any render-graph or renderer change, alongside `--smoke-test`; like it, it needs a GPU and runs locally only.

**Game executable** — the project as a player runs it (`Game/`, a console in Debug and a plain window in Release, linking no ImGui):
```
Binaries\windows-x86_64\Debug\Game.exe [--frames N] [--project <folder or Project.yaml>]
```
Plays the project's startup scene through HedgehogRuntime's `GameRuntime` (`UseProjectWindow`: the window's title, size and fullscreen come from `Project.yaml`; vsync is stored but not applied yet) until the window closes or N frames have run. The project is the nearest `Project.yaml` above the executable (a package's own folder), else the dev tree's `Projects/FeatureTest` (so it runs from any working directory), or the one `--project` names (through `FS::SetProjectRootDirectory` since HE-292, so the engine's own files still come from the engine root above the executable; a path with no `Project.yaml` exits 1). **Engine and project roots** (since HE-291, FileSystem's `api/PathUtils.hpp`): `GetEngineRootDirectory()` is the `SetEngineRootDirectory` override, else `FindEngineRoot` of the executable's folder, the nearest folder holding `ENGINE_ROOT_MARKER` (`Engine.yaml`, at the repository root, and copied into every package by the Cooker through `GetEngineRuntimeAssets`, so a package inside the repository, `Build/<name>`, is its own root), else the executable's folder; `GetProjectRootDirectory()` is the `SetProjectRootDirectory` override, else `FindDefaultProjectRoot(executable folder, engine root)` (since HE-296): the nearest folder at or above the executable holding `Project.yaml` (a package, which is both roots), else `<engine root>/Projects/FeatureTest` (`FS::DEFAULT_PROJECT_DIRECTORY`) when it holds one (the dev tree's sample), else the engine root. **Mounts** (since HE-292, `EngineContext::InitFileSystem`): `engine://` at the engine root and `shaders://` under it (the engine's own files), `project://` (`FS::PROJECT_ALIAS`) at the project root and `assets://` at its `Assets/` (the game's); `Project.yaml` (`ProjectSettings::PATH`) and `engine_settings.yaml` (`HedgehogSettings::Settings::PATH`, the project's layer names and shadow map, which ship with it) are read and written through `project://` by the Editor, `GameRuntime` (whose pre-read of the project mounts `project://` alone) and the Cooker; `--game-mode` names scenes as `assets://Scenes/<file>`. `FindAncestorHolding(start, relativeFile)` is the shared search under `FindProjectRoot` and `FindEngineRoot`; `GetLocalAppDataDirectory()` (shared with `GetSavesDirectory`), `MakeEditorUserDirectory(localAppData)` and `GetEditorUserDirectory()` (`<LocalAppData>/HedgehogEngine/Editor`, the editor's per-user state: since HE-295 `EditorApplication::Init` creates it and mounts it as `user://` (`EditorSettings::USER_ALIAS`; a temp folder when LocalAppData is not set), and it holds `editor_settings.yaml` (`EditorSettings::PATH`) and ImGui's `imgui.ini` (`ImGuiLayer` takes its path), which are no longer in the repository and are gitignored there). `FileSystemManager::ToVirtualPath` names a file by the mount with the longest root that holds it (ties: the alias that sorts first), so a file under `Assets/` is `assets://...`, never `engine://Assets/...`, whatever the registration or map order. **Engine content** (since HE-294): the engine's own runtime files live in `Content/` at the engine root and are named `engine://Content/...` (`FS::ENGINE_CONTENT_PREFIX`): `Content/Models/Default` (`MeshSystem::sDefaultMeshPath`, the cube, and `sDefaultSpherePath`), `Content/Textures/Default` (`MaterialContainer::DEFAULT_CELL_TEXTURE`, a new material's base colour), `Content/Scripts/Base/ActorScript.lua` (the base every script runs on) and `Content/Fonts/Karla-Regular.ttf` (the editor's UI font, which Hud.yaml uses too); a package holds them at `Content/`. A component's asset path may name a mount: `FS::ToAssetVirtualPath(path)` keeps a path holding `://` and puts any other under `assets://` (`FS::ASSETS_ALIAS`), and `FS::MakeAssetKey(path)` (since HE-338) is the key one asset file is known by however it is spelt (backslashes as slashes, `.` segments and repeated slashes folded, `assets://` dropped, any other mount kept, case kept, `..` left as written; `ToAssetVirtualPath` of the key names the file), and ContentLoader's `LoadMesh`, `LoadTexture`, `LoadFont` and `LoadAnimations`, `MeshSystem`'s existence check and the `AudioSystem` go through it, so `engine://Content/Models/Default/cube.obj` loads as `Models/crate.obj` does. The shipped scenes, `LampPost.prefab` and `test3.material` name the defaults that way; a scene saved before naming `Models\Default\cube.obj` loses its cube (one error, the fallback mesh used). Scripts still set only `assets://` paths. Exits nonzero when the game does not start or on any Vulkan validation error (counted after teardown).

**Lua debugger** — VS Code attaches to the scripts of the running editor (in Play), `--game-mode` or `Game.exe` when `engine_settings.yaml` has `lua_debugger: { enabled: true, port: 4711 }` (off by default: nothing is created, no thread, socket or hook). Install `Tools/VSCode/hedgehog-lua-debug` (its README: **Developer: Install Extension from Location...**, and an `attach` configuration of type `hedgehog-lua`); `python Tools/VSCode/hedgehog-lua-debug/dap_check.py <script.lua> <line>` drives the same session without VS Code (attach, break, stack, locals, one step, continue, detach; nonzero on failure). While a script is stopped the frame waits inside it: the window polls its events and its title ends with " - Paused in debugger".

**Cooker** — packages a project's assets (`Tools/Cooker/`, a console tool over the `CookerCore` static library, `Tools/CookerCore/`, namespace `Cooker`, which logs nothing and returns every problem as text, so the Editor can share it; both link HedgehogEngine, HedgehogSettings, EcsSerialization and FileSystem, the tool Logger too):
```
Binaries\windows-x86_64\Debug\Cooker.exe --project <folder> --out <folder> [--scene <assets://...yaml>]... [--glslc <glslc.exe>] [--binaries <folder>] [--engine <folder>] [--package]
```
**Packaging** (since HE-301, `CookerCore/Package.hpp`): `--package` calls `PackageGame(PackageDesc { ProjectRoot, EngineRoot, OutDir, BinariesDir, ExtraScenes, Glslc })` -> `PackageResult { Files, Copied, Unchanged, Removed, ShadersCompiled, Errors, Warnings }`, everything that makes the folder a game but building the engine and running it: `CompileEngineShaders(engineRoot, glslc)` (the stale engine shaders; `ShaderCompileResult { Compiled, Errors, Warnings }`), the cook plan with `GAME_RUNTIME_FILES` (Game.exe and the 13 DLLs it loads, the one list of them; virtual paths `runtime:<file>`) from `BinariesDir` and `LICENCE_FILES` (`LICENSE.txt`, `THIRD_PARTY_NOTICES.md`; `licence:<file>`) from the engine root added at the package root (a missing one, `The runtime file <path> does not exist.` / `The licence file ...`, is a plan error, so nothing is copied), the incremental cook (the manifest covers them all, so a repackage copies only what changed and removes a plugin disabled since), then `FindForbiddenPackageFiles(outDir)`: an `Editor.exe`, `Cooker.exe` or `*Test.exe`, a `.pdb`, `.ilk` or `.lib`, `DialogueWindows.dll`, anything named `imgui` or a GLSL source (`.vert`, `.frag`, `.comp`, `.glsl`) fails the package, `The package must not contain <path>.`. Without `--package` the Cooker cooks as before. `--all-scenes` (`PackageDesc::AllScenes`; since HE-303) cooks every scene directly in the project's `Assets/Scenes` (`ListProjectScenes(projectRoot)`, `assets://Scenes/<file>.yaml` sorted) beside the startup scene; `PackageGame.bat` and Build Game both pass it, so they still make the same folder and every scene of a project ships. **Build Game** (since HE-302): the Editor links `CookerCore`, and File > Build Game... (`Tools/BuildGameWindow`, in Edit and Play: it packages the project as saved on disk) calls the same `PackageGame` for the open project: an output folder (Browse...; by default `<engine root>/Build/<project name>`, where `PackageGame.bat` puts it), the binaries folder from the ImGui-free `Tools/GameBinaries` `ChooseGameBinaries(engineRoot, ownDir)` (`<engine root>/Binaries/windows-x86_64/Release` when it holds `Game.exe`, else the editor's own folder with a warning: build Release first, or a Debug package needs the debug C++ runtime), Build (on the main thread; the editor waits), then the counts, warnings and errors (each also in the Console as `[Build] ...`; a failed cook copies nothing), Show in Explorer and Run (`Platform/ShellActions`' `LaunchDetached`, `Game.exe` started from the output folder).
The project is the folder holding `Project.yaml`, anywhere on disk; the engine is `--engine`, by default the engine root of the Cooker itself (`FS::GetEngineRootDirectory`, the folder holding `Engine.yaml` above it; since HE-293). It first compiles every engine shader source whose `.spv` is missing or older (`<engine>/HedgehogEngine/HedgehogRenderer/assets/Shaders`, with `<engine>/ThirdParty/glslc/glslc.exe` unless `--glslc` names one; an engine without the sources or glslc is packaged as last compiled, with a warning), then builds a cook plan (`CookPlan.hpp`, `Cooker` namespace: `BuildCookPlan(projectRoot, extraScenes, binariesDir, engineRoot)`, `engine://` mounted at `engineRoot` (the project root when empty) and `project://` and `assets://` at the project: the `AssetDependencyCollector` closure of the startup scene, each `--scene`, and HedgehogEngine's `GetEngineRuntimeAssets()` (the project, the settings and input actions when present, the default cube, sphere and cells texture, and the shipped `scene`, `game` and `result` graphs with their shaders); a missing reference, `<path> (referenced by <asset>) does not exist.`, a project without a startup scene and a path outside `engine://`/`assets://` are errors) and copies it (`CookPackage`) into the package laid out as `EngineContext::InitFileSystem` mounts it: `engine://X` and `project://X` at `<out>/X` (a package's root is both roots; the Cooker mounts `project://` at the project root too), `assets://X` at `<out>/Assets/X` (`ToPackagePath`, which refuses a `..` leaving its mount); two different files with one package path (`engine://X` and `project://X` from two folders) fail the plan, `<X> is both engine://X and project://X, which are different files.`, and one file reached by both names ships once. Since HE-285 the plan also holds each plugin `Project.yaml` enables (`BuildCookPlan`'s third argument, `binariesDir`; `--binaries`, by default the Cooker's own folder): `<binariesDir>/<name>.dll` copied to the package root, beside `Game.exe` and `HedgehogEngine.dll` where the engine looks for plugins, as virtual path `plugin:<name>` (`PLUGIN_PATH_PREFIX`); an enabled plugin whose DLL is not there (`The plugin '<name>' is enabled, but <path> does not exist.`, or `... but no binaries folder was given.`) is an error, and a disabled one is not packaged. `<out>/manifest.yaml` (`version: 1`, then each file's `path`, `size` and FNV-1a 64 `hash`) makes a second cook copy only files whose source changed or whose copy is gone, and remove files the project no longer references, so the package holds the closure and nothing else. Any error prints each message and exits 1 before anything is copied. `Game.exe --project <out>` plays the package.

**Packaging a game** — one command builds the playable folder `Build\<ProjectName>\` (`Project.yaml`'s `name`; `Build/` is gitignored):
```
Scripts\PackageGame.bat [project folder]
```
The project is the folder named (relative to the caller's folder; one without `Project.yaml` fails), by default `Projects\FeatureTest`, so `Build\FeatureTest\`. It builds Release (`Build.bat`), makes the folder with one `Cooker.exe --package --all-scenes` call (every scene of the project; `--project` the project, `--engine` the repository, `--binaries` the Release folder; incremental, so a repackage copies only what changed and a plugin disabled since is removed): the assets, the enabled plugins, `Game.exe` and the DLLs it loads (`Cooker::GAME_RUNTIME_FILES`: `glfw`, `Logger`, `FileSystem`, `HedgehogMath`, `HedgehogCommon`, `ECS`, `EcsSerialization`, `ContentLoader`, `HedgehogSettings`, `HedgehogWindow`, `HedgehogAudio`, `HedgehogPhysics` (since HE-312), `HedgehogEngine`; a new DLL the game links must be added there) and `LICENSE.txt` with `THIRD_PARTY_NOTICES.md` (every third-party library, font and sample asset with its licence; add an entry when adding one), failing if the folder holds an editor, Cooker or test executable, a `.pdb`, `.ilk` or `.lib`, `DialogueWindows.dll`, anything named `imgui` or a GLSL source; then it copies the folder to `%TEMP%` and runs `Game.exe --frames 120` there (`start /wait`, the Release game being a windowed app), failing on a nonzero exit. The folder runs on a machine with only the Vulkan runtime and the VC++ redistributable; saves go to the player's LocalAppData as usual.

**Regenerating solution** after modifying any `Build.lua` files:
```
Vendor\Binaries\Premake\Windows\premake5.exe --file=Build.lua vs2022
```

**CI:** `.github/workflows/ticket-check.yml` fails any PR whose title carries no `HE-<number>` key, and `module-boundaries.yml` runs `Scripts\CheckModuleBoundaries.ps1` and its `-SelfTest` (see *Architecture*). There is currently **no build workflow** — Debug/Release builds and the test exes must be run locally before opening a PR (the smoke test is local-only in any case: CI runners have no Vulkan GPU).

## Performance

- **Frame budget: 16.6 ms (60 FPS) in Release** at default window size on the baseline machine. Weigh this in any plan touching the frame loop, render passes, ECS iteration, or per-frame allocations.
- **No optimization without a before/after number.** Measure with:
  ```
  Binaries\windows-x86_64\Release\Editor.exe --benchmark [frames] [scene.yaml]
  ```
  It loads `Assets/Scenes/benchmark.yaml` (or the named file under `Assets/Scenes/`, e.g. `Default.yaml`), warms up 120 frames, measures 600, and logs CPU timings (avg/min/max/p95) for `RenderFrame(total)` and each render-graph pass (summed over the views that ran it) plus wall frame time and FPS. Always Release; run before and after the change and quote both numbers. Baseline table and methodology: `PERFORMANCE.md`.
- Per-pass rows are CPU record times (barriers plus the pass's closure, `RenderGraphRuntime::GetLastPassTimings`); GPU-bound waiting shows up in `RenderFrame(total)`, which includes the fence wait, acquire, submit and present. For GPU-side detail, connect the Tracy 0.13.1 server (client is linked in Release, `TRACY_ON_DEMAND`); zones via `HH_PROFILE_ZONE` in `HedgehogRenderer/src/Profiling/Profiler.hpp`.

## Architecture

The engine is a set of C++20 libraries (mix of static and shared) with an `Editor` executable as the entry point. Dependencies flow strictly upward:

```
Game (ConsoleApp / WindowedApp) the player's executable: HedgehogRuntime and what it links, no ImGui
Cooker (ConsoleApp, Tools/)     packages a project: CookerCore (static lib, Tools/CookerCore: the cook and
                                PackageGame, also linked by the Editor's Build Game) → HedgehogEngine,
                                HedgehogSettings, EcsSerialization, FileSystem
Editor (ConsoleApp)            owns ImGui: context, GLFW backend, GUI renderer (RHIImGui)
  └── HedgehogRuntime + HedgehogEngine + HedgehogExtract + HedgehogScripting + HedgehogRenderer + RHIImGui
      + HedgehogWindow + HedgehogSettings + HedgehogCommon + DialogueWindows + ECS + FileSystem
      + Logger + Lua + imgui + ImGuizmo
```

`Scripts\CheckModuleBoundaries.ps1` enforces six rules on `#include` strings: no include reaches into another module's `src/`; nothing under `HedgehogRenderer/` includes `ECS/`, the engine module (`HedgehogEngine/HedgehogEngine/`, `HedgehogEngine/api/`), `imgui.h` or `imgui_impl_*`; and nothing under `HedgehogEngine/HedgehogEngine/` (tests included) includes Lua (`Lua/...`, `lua.h`, `lualib.h`, `lauxlib.h`, `lua.hpp`), sol2 (`sol/...`) or `HedgehogScripting/...`, the scripting library above it; and nothing under `HedgehogRuntime/` or `Game/` includes `imgui.h` or `imgui_impl_*`, so the Game executable links no editor UI; and (since HE-282) nothing under `Plugins/` includes ImGui, Lua, sol2 or `HedgehogScripting/...`, since plugins are engine-side; and (since HE-305) only files under `HedgehogPhysics/src/` include Jolt (`Jolt/...`), so no public header and no other module ever names a Jolt type. Each include is reported once, however many patterns it matches. `-SelfTest` builds a throwaway tree shaped like the repository, plants one violation of each kind (a cross-module `src/` include, the renderer including the ECS and `imgui.h`, the engine including Lua (`ThirdParty/Lua/lua/lua.h`, `lauxlib.h`), `sol/` and `HedgehogScripting/`, the runtime including `imgui.h` and `backends/imgui_impl_glfw.h`, `Game` including `imgui.h`, a plugin including `imgui.h`, an `imgui_impl_*` backend, `lua.h`, `sol/` and `HedgehogScripting/`, HedgehogPhysics' `api/` and the engine module including Jolt), checks each gives exactly one violation and that the tree passes without them (a `HedgehogScripting` module including sol2, the `Editor` including `imgui.h` and `HedgehogPhysics/src/` including `Jolt/Jolt.h` included), and lists each case it caught. `RunTests.bat` runs the check and then the self-test before building, and CI (`module-boundaries.yml`) runs both as separate steps.

**The renderer is being rewritten.** `RENDERING.md` at the repository root is the design: a camera-and-view architecture where a `CameraComponent` carries scene data, a `View` is the render request, and each view owns a render graph. Every frame now renders through it (see *Rendering a frame* below), and the legacy fixed-pass renderer is deleted. Epic [HE-63](https://viktoravoitovych.atlassian.net/browse/HE-63) lands it as 28 sub-1000-line pull requests.

### HedgehogRenderer Structure

The renderer follows a strict `api` / `src` split:

```
HedgehogRenderer/
├── api/
│   └── HedgehogRenderer/
│       └── Renderer.hpp          ← sole public header
└── src/
    ├── Renderer/Renderer.cpp
    ├── RHIContext/               ← owns IRHIDevice + IRHISwapchain
    ├── Renderer/FrameRenderer    ← the frame: per-frame command lists, fences and semaphores,
    │                               views, shared phase, per-view graphs, present
    ├── Graph/                    ← the render graph, graph assets, engine pass types
    │   └── Passes/               ← one .hpp/.cpp per engine pass type, plus PassCommon
    ├── GraphPasses/              ← GraphPassServices: pipelines and uniform rings for the passes
    ├── Views/, Targets/, Frame/  ← ViewManager and culling, RenderTargetRegistry, SharedPhase
    ├── ResourceRegistry/         ← mesh/material GPU buffers and descriptor sets
    └── Pipeline/, Profiling/     ← .shader/.pl loading; FrameStats and Tracy zones
```

`api/` is the public include root (added to dependents' include paths).  
`src/` is private — never included from outside the module.

### Rendering a frame (HedgehogRenderer)

Every frame goes through the render graph: the Editor (and `--game-mode`) builds a `Renderer`, simulates, extracts a `RenderScene`, calls `SyncResources`, then `Renderer::RenderFrame`, which owns the frame lifecycle inline (fence wait, resize before acquire, shared phase, per-view graphs, one execute, present) in `src/Renderer/FrameRenderer`. The editor has three views (RENDERING.md section 7): **scene** (the flycam into the `scene` target), **game** (the scene's camera, redirected to the `game` target with `SetCameraTargetOverride`), and **result** (no camera; the `result` graph's `Ui` pass draws the editor into `main`, sampling both panel targets). A hidden panel tab is sized 0x0, so its view is dropped and its passes never declared (`GetLastFramePassCount`).

Graph passes (`assets/Graphs/*.graph`; each pass type is one `.hpp`/`.cpp` pair in `src/Graph/Passes/` exposing `Get<Name>PassType()`, its slots, parameters and build function, and `EnginePassTypes` registers them): the shared phase's **Shadow** (the cascaded shadow atlas, once per frame), then per view **DepthPrepass** → **Forward** (lit, samples the atlas, into the view's HDR target) → **Skybox** (the environment where nothing was drawn) → **ForwardTransparent** (Transparent materials, blended back to front) → **ToneMap** (onto the LDR colour output) → **SelectionOutline** and **Gizmo** (scene view only: the selection's outline, then the frame's debug lines) or **GameUi** (game view only), and the result view's **Ui** (the application's `UiCallback` into `main`). **HDR and tone mapping** (since HE-325): `game.graph` and `scene.graph` declare a transient `hdr` (`R16G16B16A16Float`, the view's size) that Forward renders radiance into (the forward pipelines' colour format), and the `ToneMap` pass (`src/Graph/Passes/ToneMapPass`, slots `hdr`, sampled, and `color`, written whole with `LoadOp::DontCare`) draws one fullscreen triangle (`ToneMap.shader`: `ToneMap.pl` (set 0, the sampled texture; 16-byte fragment push constants), no vertex description, `Fullscreen/Triangle.vert` making the triangle from `gl_VertexIndex`, `ToneMap/Aces.frag`: the radiance times the exposure, then Narkowicz's ACES filmic fit, the result linear for the sRGB swapchain to encode) through `EnginePipeline::ToneMap` (no depth attachment) into the unchanged `R16G16B16A16Unorm` colour output, which Gizmo and GameUi then draw over, so overlays are never tone mapped. The exposure is `GraphFrameData::Exposure`, in EV, which `FrameRenderer::FillSceneFrame` takes from `RenderScene::Environment` (0 without one) and `MakeToneMapPushConstants` turns into `2^EV` (a non-finite one 0 EV). The pass samples a graph transient only known at execute time, through `IGraphPassServices::AllocateSampledTexture(texture)`: a set of `GraphPassServices`' per-frame-in-flight ring (`SAMPLED_TEXTURES_PER_FRAME` 16, the ToneMap shader's set-0 layout), written with the texture and a linear clamp-to-edge sampler as it is handed out. HedgehogCommon's `PASS_TYPE_SHADERS` lists `TONE_MAP_SHADER` for `ToneMap`, so a graph with the pass packages it. It costs about 0.1 ms per frame on `benchmark.yaml` (`PERFORMANCE.md`). **Game UI:** `Renderer::RenderFrame` first has the registry load the frame's `RenderScene::UiTextures` (`ResourceRegistry::SyncUiTextures`: each path's texture through the shared texture cache (which, since HE-320, uploads every texture with a full mip chain generated on the GPU; the font atlases and the white texture keep one level), magenta when missing, and a set in the GameUi shader's set-0 layout sampled clamped to the edge, at most `MAX_UI_TEXTURE_SETS` (256) with one warning past it, one per file (since HE-339 keyed by `FS::MakeAssetKey`, so every spelling of one image shares a set and counts once, each spelling seen remembered so `FindUiTextureSet` allocates nothing per frame), plus a 1x1 white set for solid fills; the layout comes from `GraphPassServices::ProvideUiTextureLayout`), and `Renderer::SyncResources` uploads every font the catalog baked since the last frame (`ResourceRegistry::SyncFonts`: the R8 atlas expanded to white with the coverage in alpha, so text needs no shader of its own, one set each in the same pool, at most `MAX_UI_FONT_SETS` (64) with one warning past it). `FrameRenderer::FillUiFrame` uploads `RenderScene::Ui` once per frame into a per-frame-in-flight vertex and 16-bit index buffer (`GraphPassServices::UploadUiGeometry`, grown on demand from `MIN_UI_VERTEX_CAPACITY`/`MIN_UI_INDEX_CAPACITY`) and fills `GraphFrameData::UiCommands`, `UiVertices`, `UiIndices`, `UiTextureSets` (per `UiTextures` entry, null when not loaded), `UiFontSets` (per `UiFonts` entry, null past the budget), `UiSolidTexture` and `UiTargetSize` for every view. The `GameUi` pass (`src/Graph/Passes/GameUiPass`, slot `color`, after Forward in `game.graph`, not in `scene.graph`) loads the colour, binds `EnginePipeline::GameUi` (`GameUi.shader`: `GameUi.pl` (set 0, one texture; 16-byte push constants), `Ui.vdes` (one interleaved 20-byte stream: position and UV as `r32g32_float`, colour as `r8g8b8a8_unorm`, a format `VertexDescLoader` now reads), alpha blending, no depth test and no depth attachment), pushes `MakeGameUiPushConstants(UiTargetSize)` (pixels, y down, onto clip space, so a UI laid out for one size stretches over the colour target it draws into) and records each command as a scissor (`MakeGameUiScissor`: scaled to the colour target, rounded outward, clamped, the command skipped when empty), its texture (its font's set for a `UI_FONT_TEXTURE` command, which is skipped when the font has none; the white set for `UI_NO_TEXTURE` or a texture that did not load) and one `DrawIndexed`. A frame without commands, geometry or the white set records nothing. `GameUi/Quad.vert` decodes the vertex colour from sRGB, as the pickers and textures are, and the fragment shader multiplies it by the texture. **Debug lines** (since HE-316): `HX::RenderScene::DebugLines` is a generic list of world-space vertex pairs (`HX::DebugLineVertex { Position, Color }`, an `HM::Vector3` and an RGBA8 colour, red lowest, picked in sRGB; 16 bytes), emptied by `Clear` and nothing the renderer knows the source of (HedgehogExtract's `ExtractPhysicsDebug` fills it with collider wireframes, so the renderer still never needs the ECS); `FrameRenderer::FillUiFrame` uploads it once per frame (an odd last vertex dropped) into a per-frame-in-flight vertex buffer (`GraphPassServices::UploadDebugLines`, grown on demand from `MIN_DEBUG_LINE_VERTEX_CAPACITY`, null when empty) and fills `GraphFrameData::DebugLineVertices`/`DebugLineVertexCount` for every view. The Gizmo pass records nothing without lines (since HE-353 it no longer draws the selection's bounds boxes: `Gizmo.shader`, `Gizmo/Box.*`, `GetGizmoBoxLines` and `MakeGizmoBoxMatrix` are gone); otherwise it binds `EnginePipeline::DebugLines` (`DebugLines.shader`: `line_list` over `PositionColor.vdes` (`r32g32b32_float` position, `r8g8b8a8_unorm` colour), the Gizmo pipeline layout with its viewProj set 0, depth tested and not written, `DebugLines/Line.vert` decoding the colour from sRGB as `GameUi/Quad.vert` does) and makes one `Draw` of every line. **Selection mask** (since HE-352, epic HE-350): the `SelectionMask` pass type (`src/Graph/Passes/SelectionMaskPass`, slot `mask`), in `scene.graph` only (a transient `selectionMask`, `R8Unorm`, at the view's size), clears the mask and draws the view's `OverlayInstances` (the editor's selection, on the editor layer) into it as 1 through `EnginePipeline::SelectionMask`/`SelectionMaskSkinned` (`SelectionMask.shader`/`SelectionMaskSkinned.shader`: the depth prepass's layouts and vertex shaders, `SelectionMask/Mask.frag`, no depth attachment, depth test and face culling off, so the whole silhouette is marked even where the scene hides it; a skinned selection needs the frame's palette), recording nothing without a selection. **Selection outline** (since HE-353): the `SelectionOutline` pass type (`src/Graph/Passes/SelectionOutlinePass`, slots `color` and `mask`), after ToneMap and before Gizmo in `scene.graph` (`color: color`, `mask: selectionMask`), samples the mask through `AllocateSampledTexture` and draws one fullscreen triangle over the loaded colour through `EnginePipeline::SelectionOutline` (`SelectionOutline.shader`: `ToneMap.pl`, `Fullscreen/Triangle.vert`, `SelectionOutline/Outline.frag`, alpha-blended, no depth attachment): a pixel outside the mask with a masked pixel within `SELECTION_OUTLINE_WIDTH` (2 px; `MakeSelectionOutlinePushConstants(width, height)`: the texel size and the width, 16 bytes) turns orange, its edge softened by the distance, so the selection shows as an outline of its silhouette, hidden parts included, in place of the old bounds box; it records nothing without a selection, so a frame without one costs nothing (`PERFORMANCE.md`). It records nothing without transparent instances, so other scenes cost the same (`PERFORMANCE.md`); rigid and skinned instances are sorted apart, and nothing sorts within a mesh. **Skinned meshes:** the frame uploads `RenderScene::JointMatrices` once (`GraphPassServices::UploadJointPalette`: a storage buffer per frame in flight, at least `MIN_PALETTE_CAPACITY` matrices and grown on demand, handed to the passes as `GraphFrameData::JointPalette`). The Forward pass binds set 3 from `IGraphPassServices::AllocateForwardLighting(shadow, atlas)` (`GraphPassServices`' per-frame ring of the forward shader's set-3 layout, `FORWARD_UNIFORMS_PER_FRAME` sets, the uniform copied and the atlas written with a linear, clamped `LessOrEqual` comparison sampler each time) for its rigid and skinned draws, the atlas being the texture bound to its `shadowMap` slot; the skinned palette moved to set 4 (`GraphForwardSkinned.pl`, `Skinned.vert`'s `PALETTE_SET 4`). `Shaders/Common/Shadows.glsl`'s `SunShadow(position, geometric normal, toLight)` picks the cascade by the camera's view depth (lit past the last), pushes the position along the normal by the cascade's offset, projects it into the cascade's tile (lit outside its box), subtracts the depth bias plus the slope bias times the tangent of the angle to the light (at most 10), averages `(2r + 1)^2` hardware 2x2 comparisons one texel apart, clamped inside the tile, and across the last `CascadeBlend` of a cascade's depth range fades into the next cascade (the last fades to lit); `Base.frag` multiplies the light at `LightIndex` by it. Two latent bugs of the cascade fit, harmless while the atlas was never read, were fixed with it: the camera frustum is unprojected through the inverse of `Proj * View` (it was `View * Proj`), and each cascade's ortho maps depth to [0, 1] as Vulkan clips (`HM::Matrix4x4::Ortho` maps it to [-1, 1], so the half towards the light was clipped), its eye on the light's side of the slice (it was on the far side) `SHADOW_CASTER_REACH` (4) radii back, so casters between the light and the slice still cast; a light straight up or down takes +Y as its view's up. The editor's Scene view reads the same cascades, fitted to the game camera, so far from it the scene shows unshadowed. **PBR shading** (since HE-326): `GraphForward/Base.frag` shades rigid and skinned instances alike with glTF's metallic-roughness model from `Shaders/Common/Pbr.glsl` (which replaced `Lighting.glsl` and `SurfaceData.glsl`; `LightData.glsl`'s `Light` is kept): a Lambert diffuse lobe (none for a metal) and a Cook-Torrance specular lobe (GGX distribution, height-correlated Smith visibility, Schlick Fresnel with F0 4 % for a dielectric and the base colour for a metal; roughness clamped to at least `MIN_ROUGHNESS` 0.045 and squared), summed over the scene's lights in the pi convention (a light's colour times intensity is what a white Lambert surface facing it shows, at 1 m for a point or spot light, so scenes lit before keep roughly their brightness): a directional light from its `direction` (towards the light, normalized), a point light by inverse square from at least `MIN_LIGHT_DISTANCE` 0.1 m, windowed to 0 at its `Radius` (`RangeWindow`; a radius of 0 never fades), and a spot light likewise inside a cone whose half angle's cosine is the uniform's `data.w`, faded smoothly over the outer fifth of that cosine range (`SPOT_FADE`), shining along its `direction` as before. The surface is the base colour map times `baseColorFactor`, metallic and roughness the factors times the metallic-roughness map's B and G, and, when the material has a normal map (`TextureFlags` bit 1), the normal bent by it through the interpolated tangent basis (Gram-Schmidt, handedness from the tangent's w, xy scaled by `NormalScale`); the emissive map times `EmissiveFactor` is added, and the result is HDR radiance for the ToneMap pass. The scene's environment adds ambient light (see **Image-based lighting** below); without one there is no ambient term, so a surface no light reaches (and a metal away from its highlights) is black. The vertex shaders turn the tangent by the model (`Base.vert`) or skinned model matrix (`Skinned.vert`) and pass it on at location 3; `FullMesh.vdes` gains the tangent binding 3 and `SkinnedFullMesh.vdes` has positions, UVs, normals, tangents, joints and weights at bindings 0 to 5, which `ForwardPass` binds in that order (four streams for rigid instances, six for skinned; it records only its clear without the tangent stream). On `benchmark.yaml` it costs nothing measurable (`PERFORMANCE.md`). **Image-based lighting** (since HE-331): `FrameRenderer` owns an `EnvironmentResources` (`src/Environment/`), which `Renderer::RenderFrame` syncs with `RenderScene::Environment` after the UI textures (`FrameRenderer::SyncEnvironment`): the first time a map's path is seen it is baked with ContentLoader's `BakeEnvironment` and uploaded as an `R16G16B16A16Float` cube with every mip, face by face through region copies, and kept for the session (`GetBakedCount`), so a second scene or switching back bakes nothing; a map that does not bake has logged its error and is remembered, never tried again. At start it computes the split-sum BRDF table (`BRDF_LUT_SIZE` 64, `BRDF_LUT_SAMPLES` 256; `R16G16Float`) and a black 1x1 cube, the fallback for no environment or a failed one. `FillSceneFrame` hands every view `GraphFrameData::Environment`, a `ForwardEnvironment { Uniform, Radiance, BrdfLut }` (`api/HedgehogRenderer/Graph/EnvironmentUniform.hpp`): `EnvironmentUniform` (std140, 160 bytes: the nine SH coefficients times the intensity, `Intensity`, `RotationCos`/`RotationSin` of the turn about +Z and `MaxMip`), built by the pure `MakeEnvironmentUniform(sh, mipCount, intensity, rotationDegrees)` (non-finite values as 0, a negative intensity as 0), or `MakeNoEnvironmentUniform()` (all zero: no ambient light). The forward pipelines' set 3 (`GraphForward.pl`, `GraphForwardSkinned.pl`) gained binding 2, the environment uniform (in the same per-slot buffer as the shadow uniform, at offset 512), binding 3, the radiance `samplerCube`, and binding 4, the BRDF table, both through the linear clamp sampler; `IGraphPassServices::AllocateForwardLighting(shadow, atlas, environment)` copies both uniforms and writes the three textures each time, so the rigid and skinned draws share one set. `Common/Pbr.glsl`'s `AmbientLight(surface, occlusion)` turns directions back by the rotation (`EnvironmentDirection`), adds the base colour times (1 - metallic) times the SH irradiance at the normal (`EnvironmentIrradiance`, ContentLoader's basis) and the radiance prefiltered at `roughness * maxMip` along the reflection times `F0 * scale + bias` from the table at (N.V, roughness), all times the occlusion map (`1 + occlusionStrength * (R - 1)`, ambient light only, as glTF defines it); `Base.frag` adds it after the lights. It costs nothing measurable per frame; a bake takes 179 ms in Release for a 256x128 sky at face 256 (`PERFORMANCE.md`). **Skybox** (since HE-332): `ForwardEnvironment::ShowSkybox` is true when the frame's map baked and its component's `ShowSkybox` is on; the `Skybox` pass type (`src/Graph/Passes/SkyboxPass`, slots `color`, written over with `LoadOp::Load`, and `depth`, read-only), between Forward and ToneMap in `game.graph` and `scene.graph` (`color: hdr`, `depth: depth`), then draws one fullscreen triangle at the far plane through `EnginePipeline::Skybox` (`Skybox.shader`: `Skybox.pl`, set 0 one combined image sampler, the same layout as ToneMap's, so the cube comes from `AllocateSampledTexture`, and 80 bytes of fragment push constants; `Skybox/Sky.vert` places the triangle at depth 1, `Skybox/Sky.frag` reads the cube at mip 0 along the pixel's direction, turned back by the rotation, times the intensity; depth tested `less_or_equal` against the prepass's cleared 1, not written; the HDR format and the depth format), so it shows only where nothing was drawn. `MakeSkyboxPushConstants(view, proj, environment)` gives `SkyboxPushConstants` (the inverse of `proj * view` with the view's translation removed, so the sky stays at infinity, then the rotation's cosine and sine and the intensity). It records nothing without a frame context, a baked environment or with `ShowSkybox` off, so the clear colour (black) stays. HedgehogCommon's `PASS_TYPE_SHADERS` lists `SKYBOX_SHADER` for `Skybox`, so `game.graph`'s closure ships it. It costs 0.007 ms to record (`PERFORMANCE.md`).

The legacy fixed-pass renderer is gone: `DrawFrame`, every legacy pass, `RenderQueue` and `ResourceManager` with its textures. Render order comes from the graph compiler's topological sort, render targets are either pooled graph transients or view-owned targets in the render-target registry, the `Renderer` owns the mesh/material `ResourceRegistry` directly (**materials**, since HE-324: each material's set 1 of the forward pipelines (`GraphForward.pl`, `GraphForwardSkinned.pl`) is binding 0, `MaterialUniform` (`src/ResourceRegistry/MaterialUniform.hpp`, std140, 64 bytes: `BaseColorFactor`, `EmissiveFactor`, `Metallic`, `Roughness`, `NormalScale`, `OcclusionStrength`, `Transparency` and `TextureFlags`, a bit per slot whose map the material names; built by the pure `MakeMaterialUniform(MaterialView)`), then bindings 1 to 5, one combined image sampler per `MaterialTextureBinding` (BaseColor, Normal, MetallicRoughness, Occlusion, Emissive): the slot's map, uploaded as sRGB for colour (base colour, emissive) and linear `R8G8B8A8Unorm` for data, the texture cache keeping one copy per file and colour space (keyed by `FS::MakeAssetKey`, since HE-338, so `Models\a.png` and `Models/a.png` share one upload; the game UI's images go through the same cache), or else its neutral default (1x1 white sRGB, white linear, or the flat normal (128, 128, 255)), so factors pass through unchanged; `GraphForward/Base.frag` reads them all (see **PBR shading** below); The Editor's render graph editor (`Editor/Tools/RenderGraphEditor/`) draws and edits a graph with them: its edits are plain `GraphAsset` operations in `GraphEditing`, it checks every edit with `DiagnoseGraph` (problems in red on their node, and in a list under the canvas), it saves through `GraphAssetWriter` and the renderer hot-reloads the file, and node positions live in a `<name>.graph.layout` file beside the graph. New starts an empty untitled graph, Open... and Save As... pick any `.graph` file (`DialogueWindows::RenderGraphOpenDialogue`/`RenderGraphSaveDialogue`), and a picked file is named by `MakeGraphReference` (`Tools/RenderGraphEditor/GraphFileReference`): an engine graph's name, else a virtual path under the most specific mount, else an absolute path, normalized as the renderer lists it, and registered with `Renderer::LoadGraph`. The camera inspector (`EditorGui::DrawCameraGraph`) names the same references: its drop-down shows engine graphs by name and files by file name, Browse... picks a file through the same dialogue and `MakeGraphReference`, Edit opens the camera's graph with `RenderGraphEditorWindow::OpenGraph`, and a reference with no usable graph shows in red with the renderer's reason.

**ImGui belongs to the Editor, never the renderer.** `Editor/ImGuiLayer` owns the context, the GLFW platform backend and the GUI renderer (`RHIImGui::IGuiRenderer`, ImGui's Vulkan backend with dynamic rendering into any texture of one colour format, created in the `Renderer`'s `DeviceReadyCallback`, which hands the application the device and the swapchain's format once at construction). The result view's `Ui` pass hands the editor its colour target through a `UiCallback`. Neither `HedgehogRenderer` nor `RHI` has an ImGui include path or link, and the boundary check keeps it that way.

### Third-Party Dependencies (git submodules)

glfw, ImGui, imgui-node-editor (the Editor's render graph canvas), ImGuizmo (the Scene view's transform gizmos; since HE-354), yaml-cpp, tinygltf, doctest, Lua, sol2, Tracy, miniaudio, Jolt Physics — all under `ThirdParty/`, each pinned to a commit of a fork under `vVoitovych`. The imgui-node-editor fork carries a small patch for the ImGui version in use; update it there, not in the submodule's working tree. ImGuizmo (`ThirdParty/ImGuizmo/ImGuizmo`, MIT) is pinned to 18cef5e (upstream master, 2026-08-08; it builds against our ImGui unpatched) and built as the `ImGuizmo` static library by `ThirdParty/ImGuizmo/Build-ImGuizmo.lua` (`src/ImGuizmo.cpp` alone, not the repository's other widgets; warnings off), linked by the Editor only (`IncludeDir.ImGuizmo` is its `src`); include `imgui.h` before `ImGuizmo.h`, which does not include it. Lua is pinned to the `v5.4.9` release (312b9efa): the scripting epic binds it with sol2, which does not handle Lua 5.5's `lua_newstate(seed)`, so stay on the 5.4 line until sol2 supports 5.5. sol2 (header-only, `ThirdParty/sol2/sol2`) is pinned to 9190880c, the v3.5.0 release commit (the fork has no tags), and is included only through `HedgehogScripting/api/Sol.hpp`. miniaudio (`ThirdParty/miniaudio/miniaudio`) is pinned to 9634bedb, the 0.11.25 release commit (the fork has no tags), and built as the `miniaudio` C static lib from one `MINIAUDIO_IMPLEMENTATION` file, `ThirdParty/miniaudio/MiniaudioImpl.c`, with its warnings off as yaml-cpp's are; only HedgehogAudio's sources include `miniaudio.h`. Vulkan SDK headers/libs are also under `ThirdParty/vulkan/`. Jolt Physics (`ThirdParty/Jolt/JoltPhysics`, MIT; since HE-305) is pinned to e77f1755, the v5.6.0 release commit (the fork has no tags), and built as the `Jolt` static library by `ThirdParty/Jolt/Build-Jolt.lua` (C++20, warnings off as yaml-cpp's are, the library alone: its GPU compute backends under `Jolt/Compute/{CPU,DX12,MTL,VK}` and their `Jolt/Shaders` are left out). Jolt's configuration defines change its classes' layout, so they must be identical in `Jolt.lib` and in every project including `Jolt/Jolt.h`: they live in one `JoltDefines` table in `Dependencies.lua` (`Common`: `JPH_USE_SSE4_1`, `JPH_USE_SSE4_2`, `JPH_USE_LZCNT`, `JPH_USE_TZCNT` (no AVX, so a packaged game runs on any recent x64 CPU) and `JPH_OBJECT_LAYER_BITS=16`; `Debug`: `JPH_ENABLE_ASSERTS`; `Release`: `NDEBUG`, which Jolt reads to leave out its debug-only checks and members), applied by calling `UseJoltDefines()` in the project (it resets the filter afterwards); nothing else defines a `JPH_` macro (no debug renderer, profiler, double precision, determinism, floating-point exceptions or object stream). Nothing links Jolt until HedgehogPhysics, and only `HedgehogPhysics/src/` may include it (boundary rule 6). `ThirdParty/stb` is vendored, not a submodule: `stb_image.hpp`, and `stb_truetype.h` 1.26 as Dear ImGui ships it (`imstb_truetype.h`, upstream plus three marked warning and crash fixes), compiled once in ContentLoader's `src/FontLoader.cpp`.
