# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Workflow

**Every change starts as a Jira ticket in project `HE` and lands as one pull request under ~1000 changed lines.** Read `WORKFLOW.md` before starting any work — it defines the ticket model, the sizing rule, branch and commit conventions, and the Jira/GitHub automation.

The short form:
- Branch `HE-<n>-<slug>` off `master`; no long-lived integration branches.
- Commit subjects and PR titles start `HE-<n>: `. A `commit-msg` hook and the `ticket-check` CI job enforce this; Jira uses it to move the ticket to **In Review** on PR creation and **Done** on merge.
- Break a problem into tickets with `/jira-tickets <problem>` before writing code.

## Build System

HedgehogEngine uses **Premake5** to generate Visual Studio 2022 solution files. There is no CMake.

**Initial setup** (run once, or after submodule changes):
```bat
Scripts\SetupWindows.bat
```
This initializes git submodules recursively and generates `HedgehogEngine.sln`.

**Building (CLI — always build after code changes, a change is not done until it compiles):**
```
Scripts\Build.bat [Debug|Release]        (default: Debug; locates MSBuild via vswhere)
```
**Build + run all tests in one step:**
```
Scripts\RunTests.bat [Debug|Release]     (exits nonzero if the build or any test fails)
```
Alternatively invoke MSBuild directly (`MSBuild.exe HedgehogEngine.sln /p:Configuration=Debug /p:Platform=x64 /m /v:m`) or open `HedgehogEngine.sln` in Visual Studio 2022. Configurations: `Debug` and `Release`, platform: `x64`.

**Shader compilation** is automatic via a Shaders project pre-build command that calls `ThirdParty/glslc/CompileShaders.bat`, compiling `.vert`/`.frag`/`.comp` GLSL sources to SPIR-V (`.spv`).

**Build output:** every executable and DLL of a configuration goes to one directory, `Binaries/windows-x86_64/[Debug|Release]/`, so each program finds its DLLs next to it with no copy step. Static libraries and object files go to `Binaries/Intermediates/windows-x86_64/[Debug|Release]/[ProjectName]/`. The two directories are `BinariesDir` and `IntermediatesDir` in the root `Build.lua`.

**Running tests** (doctest; each exe exits nonzero on failure):
```
Binaries/windows-x86_64/Debug/HedgehogMathTest.exe
Binaries/windows-x86_64/Debug/FileSystemTest.exe
Binaries/windows-x86_64/Debug/ECSTest.exe
Binaries/windows-x86_64/Debug/EcsSerializationTest.exe
Binaries/windows-x86_64/Debug/ContentLoaderTest.exe
Binaries/windows-x86_64/Debug/HedgehogExtractTest.exe
Binaries/windows-x86_64/Debug/RenderGraphTest.exe
Binaries/windows-x86_64/Debug/HedgehogEngineTest.exe
Binaries/windows-x86_64/Debug/ScriptingTest.exe
Binaries/windows-x86_64/Debug/AnimationTest.exe
Binaries/windows-x86_64/Debug/UiTest.exe
Binaries/windows-x86_64/Debug/HedgehogWindowTest.exe
Binaries/windows-x86_64/Debug/InputTest.exe
Binaries/windows-x86_64/Debug/AudioTest.exe
Binaries/windows-x86_64/Debug/EditorTest.exe
```

**Renderer smoke test** — after any renderer/RHI change, run (from the repo root, needs a Vulkan GPU):
```
Binaries\windows-x86_64\Debug\Editor.exe --smoke-test [frames]
```
Renders N frames (default 120) and exits nonzero if any Vulkan validation error occurred (Debug builds enable `VK_LAYER_KHRONOS_validation`; messages route through Logger, counters live in `RHI/api/RHIDiagnostics.hpp` and are re-exported via `Renderer.hpp`).

**Game mode** — the render-graph path as a game build runs it, with no editor:
```
Binaries\windows-x86_64\Debug\Editor.exe --game-mode [frames] [scene.yaml]
```
Loads `Assets/Scenes/Default.yaml` (or the named file under `Assets/Scenes/`, e.g. `Animated.yaml`, two animated `TwoBoneStrip`s and a rigid cube, for skinned rendering, or `Hud.yaml`, a cube under a game UI canvas: a translucent top bar with a logo and a title, a health bar with its value and a tinted textured button labelled PLAY, the text in `Assets/Fonts/Karla-Regular.ttf`, SIL OFL 1.1), builds a `Renderer` exactly as the editor does, but creates no ImGui, and renders N frames (default 120) with `RenderFrame` from views derived from the scene's camera components. Exits nonzero on any Vulkan validation error **or if an ImGui context ever exists** — the renderer not depending on ImGui is checked, not assumed. Run it after any render-graph or renderer change, alongside `--smoke-test`; like it, it needs a GPU and runs locally only.

**Regenerating solution** after modifying any `Build.lua` files:
```
Vendor\Binaries\Premake\Windows\premake5.exe --file=Build.lua vs2022
```

**CI:** `.github/workflows/ticket-check.yml` fails any PR whose title carries no `HE-<number>` key, and `module-boundaries.yml` runs `Scripts\CheckModuleBoundaries.ps1` and its `-SelfTest` (see *Architecture*). There is currently **no build workflow** — Debug/Release builds and the test exes must be run locally before opening a PR (the smoke test is local-only in any case: CI runners have no Vulkan GPU).

## Performance

- **Frame budget: 16.6 ms (60 FPS) in Release** at default window size on the baseline machine. Weigh this in any plan touching the frame loop, render passes, ECS iteration, or per-frame allocations.
- **No optimization without a before/after number.** Measure with:
  ```
  Binaries\windows-x86_64\Release\Editor.exe --benchmark [frames] [scene.yaml]
  ```
  It loads `Assets/Scenes/benchmark.yaml` (or the named file under `Assets/Scenes/`, e.g. `Default.yaml`), warms up 120 frames, measures 600, and logs CPU timings (avg/min/max/p95) for `RenderFrame(total)` and each render-graph pass (summed over the views that ran it) plus wall frame time and FPS. Always Release; run before and after the change and quote both numbers. Baseline table and methodology: `PERFORMANCE.md`.
- Per-pass rows are CPU record times (barriers plus the pass's closure, `RenderGraphRuntime::GetLastPassTimings`); GPU-bound waiting shows up in `RenderFrame(total)`, which includes the fence wait, acquire, submit and present. For GPU-side detail, connect the Tracy 0.13.1 server (client is linked in Release, `TRACY_ON_DEMAND`); zones via `HH_PROFILE_ZONE` in `HedgehogRenderer/src/Profiling/Profiler.hpp`.

## Architecture

The engine is a set of C++20 libraries (mix of static and shared) with an `Editor` executable as the entry point. Dependencies flow strictly upward:

```
Editor (ConsoleApp)            owns ImGui: context, GLFW backend, GUI renderer (RHIImGui)
  └── HedgehogEngine + HedgehogExtract + HedgehogScripting + HedgehogRenderer + RHIImGui
      + HedgehogWindow + HedgehogSettings + HedgehogCommon + DialogueWindows + ECS + FileSystem
      + Logger + Lua + imgui
        ├── HedgehogExtract  (static lib) → ECS, HedgehogEngine, HedgehogMath, HedgehogUI
        ├── HedgehogAnimation (static lib) → HedgehogMath (headers only: ContentLoader's loaded
        │                                   skin and clip structs); linked by HedgehogEngine
        ├── HedgehogInput    (static lib) → HedgehogMath, FileSystem, Logger, yaml-cpp (headers only:
        │                                   HedgehogWindow's RawInput and key codes); linked by
        │                                   HedgehogEngine
        ├── HedgehogAudio    (DLL)        → miniaudio (static C lib), HedgehogMath, FileSystem, Logger;
        │                                   linked by HedgehogEngine
        ├── HedgehogUI       (static lib) → HedgehogMath (headers only: HedgehogExtract's
        │                                   UiDrawList, ContentLoader's LoadedFont); linked by
        │                                   HedgehogExtract
        ├── HedgehogScripting (static lib) → HedgehogEngine, HedgehogInput, HedgehogAudio, ECS, HedgehogMath, FileSystem, Logger,
        │                                   Lua, sol2 (header-only); registered by the Editor
        │                                   and --game-mode
        ├── HedgehogEngine   (DLL)        → HedgehogCommon, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, HedgehogAnimation, HedgehogInput, HedgehogAudio, HedgehogMath, ECS, EcsSerialization,
        │                                   FileSystem, yaml-cpp, Logger
        ├── HedgehogRenderer (static lib) → RHI, HedgehogMath, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, FileSystem, Logger, yaml-cpp, Tracy
        │                                   (headers only: HedgehogCommon, HedgehogExtract's
        │                                   RenderScene; never the ECS, HedgehogEngine or ImGui)
        ├── RHIImGui         (static lib) → RHI, imgui (ImGui's Vulkan renderer, via
        │                                   RHI/api/Vulkan/VulkanNative.hpp)
        ├── HedgehogWindow   (DLL)        → HedgehogMath, GLFW, Logger
        ├── HedgehogSettings (DLL)        → FileSystem, yaml-cpp, Logger
        ├── HedgehogCommon   (DLL)        → HedgehogMath
        └── RHI              (static lib) → Vulkan (Volk + VMA), Logger — no ImGui
```

`Scripts\CheckModuleBoundaries.ps1` enforces three rules on `#include` strings: no include reaches into another module's `src/`; nothing under `HedgehogRenderer/` includes `ECS/`, the engine module (`HedgehogEngine/HedgehogEngine/`, `HedgehogEngine/api/`), `imgui.h` or `imgui_impl_*`; and nothing under `HedgehogEngine/HedgehogEngine/` (tests included) includes Lua (`Lua/...`, `lua.h`, `lualib.h`, `lauxlib.h`, `lua.hpp`), sol2 (`sol/...`) or `HedgehogScripting/...`, the scripting library above it. Each include is reported once, however many patterns it matches. `-SelfTest` builds a throwaway tree shaped like the repository, plants one violation of each kind (a cross-module `src/` include, the renderer including the ECS and `imgui.h`, the engine including Lua (`ThirdParty/Lua/lua/lua.h`, `lauxlib.h`), `sol/` and `HedgehogScripting/`), checks each gives exactly one violation and that the tree passes without them (a `HedgehogScripting` module including sol2 included), and lists each case it caught. `RunTests.bat` runs the check and then the self-test before building, and CI (`module-boundaries.yml`) runs both as separate steps.

**The renderer is being rewritten.** `RENDERING.md` at the repository root is the design: a camera-and-view architecture where a `CameraComponent` carries scene data, a `View` is the render request, and each view owns a render graph. Every frame now renders through it (see *Rendering a frame* below), and the legacy fixed-pass renderer is deleted. Epic [HE-63](https://viktoravoitovych.atlassian.net/browse/HE-63) lands it as 28 sub-1000-line pull requests.

### Key Modules

| Module | Type | Role |
|--------|------|------|
| `HedgehogMath` | DLL | Vectors, matrices, AABB/OBB/Plane/Frustum primitives; `Quaternion` (identity, axis-angle and Euler in degrees, multiply, rotate, normalize, inverse, `Slerp`, `ToMatrix`, `LookRotation` turning local -Z to forward with +Y up). `FromEuler(e).ToMatrix()` equals TransformSystem's `GetRotationX * GetRotationY * GetRotationZ`, so a `TransformComponent` keeps storing Euler degrees; `ToEuler` gives y in [-90, 90] and z = 0 at gimbal lock |
| `HedgehogCommon` | DLL | Shared renderer constants (`MAX_FRAMES_IN_FLIGHT`, `MAX_LIGHTS_COUNT`, …), Camera |
| `HedgehogWindow` | DLL | GLFW window wrapper, input handling (namespace `HW`). Input is one record, the complete `RawInput` (`api/RawInput.hpp`, pure data): every key (`api/InputCodes.hpp`: `Key`, valued as GLFW's codes, checked by `static_assert`s in Window.cpp, `KEY_COUNT` 349; `MouseButton`, 8), the cursor position (window coordinates, y down), the cursor and scroll deltas summed since the frame began, `CursorInside` and `Focused`. It is filled by GLFW-free exported free functions (`api/RawInputEvents.hpp`): `BeginInputFrame` zeroes the deltas (`WindowContext::HandleInput` calls `Window::BeginInputFrame` before polling), `ApplyKeyEvent` (a repeat counts as down; an unknown or out-of-range code is ignored), `ApplyMouseButtonEvent`, `ApplyCursorEvent` (the first event, and the first after the cursor leaves, sets the position without a delta), `ApplyScrollEvent` (summed), `ApplyCursorEnter`, `ApplyFocus` (losing focus releases every key and button) and `ApplyGamepadState(raw, connected, buttons, axes)` (the first gamepad: `RawInput::Gamepad` is a `GamepadState` of `Connected`, 15 `Buttons` (`GamepadButton`, GLFW's standard layout: A, B, X, Y, bumpers, Back, Start, Guide, thumbs, D-pad) and 6 `Axes` (`GamepadAxis`: sticks in [-1, 1], y down, so up is -1; triggers stored in [0, 1], 0 at rest, from GLFW's [-1, 1]); not connected zeroes it all). `Window::PollGamepad()` reads the first joystick GLFW maps as a gamepad, and `WindowContext::HandleInput` calls it after polling events. `Window::GetRawInput()` is never filtered: deciding what reaches the game or the editor camera is the application's job (HedgehogInput's `MakeGameInput`). The legacy `InputState`, `GetInputState` and `SetGuiCallback` are gone; F11 still toggles fullscreen. `Window::GetWindowSize` is the client area in the cursor's coordinates, beside `GetFramebufferSize` |
| `HedgehogSettings` | DLL | YAML-based engine configuration |
| `HedgehogEngine` | DLL | Engine context; resource catalog (Material, Mesh, Texture containers); ECS systems and components; scenes (`SceneManager`: file load/save, and `CaptureSnapshot`/`RestoreSnapshot`, an in-memory `SceneSnapshot` of the YAML, scene name and game-object index; restore replaces the whole tree, brings entities back under their captured ids and runs the same post-load refresh as `LoadScene`). `Time/FixedStepClock`: a plain-data fixed-step clock (`FixedDeltaTime` 1/60, `MaxSubsteps` 8, `TimeScale`, plus accumulator, simulated `Time` and counters) with free functions `AdvanceFixedStepClock(clock, realDt)`, which returns the steps to run this frame (capped at `MaxSubsteps`, excess dropped; bad frame times count as zero; a small tolerance makes 1/30 s exactly two 1/60 s steps; bad settings fall back to the defaults), and `ResetFixedStepClock`, which keeps the settings. It has no pause flag: play mode simply stops advancing it. **Play mode** lives in `EngineContext` (`PlayState` Edit/Playing/Paused, the snapshot and the clock; the ECS only forwards events). `Play()` (from Edit) captures a snapshot, resets the clock and sends `NotifyPlayStart`; `Pause()`/`Resume()` send `NotifyPlayPause`/`NotifyPlayResume`; `Stop()` (from Playing or Paused) sends `NotifyPlayStop` (reverse order), then restores the snapshot; a call in the wrong state returns false and sends nothing. `UpdatePlayMode(dt)` (public, so tests drive frames headless) runs only while Playing: the clock's fixed steps of `RunFixedUpdate(FixedDeltaTime)`, then one `RunUpdate(dt * TimeScale)`. `UpdateContext(aspectRatio, dt)` (it needs no window; `Engine::UpdateContext(dt, aspect)` calls it) calls it before Transform, Hierarchy and Light, which run in every mode. `~EngineContext` sends `NotifyPlayStop` if still playing, without restoring. Scripts run in HedgehogScripting's `ScriptSystem`, which the application registers; the engine only stores `ScriptComponent` data (loading a scene runs no script code). The engine has no Lua of its own: it neither links nor includes Lua, and `ScriptComponent` is a pure-data struct (`Enable`, `ScriptPath`, `Properties`, an ordered `std::vector<ScriptProperty>`, and `Visit`). A `ScriptProperty` is `Name`, `ScriptPropertyType Type` (Number, Bool, Vector3, Color, String, EntityRef, AssetRef), `ScriptPropertyValue Value` (`std::variant<bool, float, HM::Vector3, std::string, ECS::Entity>`; Color is an RGB `Vector3`, AssetRef a path under `assets://`) and `AssetType` (the content type an AssetRef takes); free functions `FindScriptProperty` and `SetScriptProperty` find one by name and replace-or-append. Its YAML is the exported free function `RegisterScriptComponentSerializer(ComponentSerializerRegistry&)` (`api/Scene/ScriptComponentSerializer.hpp`), which `EngineContext` calls: it writes `ScriptProperties: { <name>: { Type: <type name>, Value: ..., AssetType (AssetRef only) } }` in order (an EntityRef as the entity id, which scene loads keep), and reads that or the legacy `ScriptParams` (`ParamType` 0 Boolean, 1 Number, value in `ParamValue`; the shipped Default.yaml stays in that format as the fixture); with both keys `ScriptProperties` wins and one warning is logged, and a property it cannot read (unknown type, wrong value) is skipped with a warning. **Animation:** a loaded `Mesh` keeps a skinned file's `HedgehogAnimation::Skeleton` (`GetSkeleton()`, nullptr for a static mesh), its clips (`GetAnimationClips()`, through ContentLoader's `LoadAnimations`, read only when the mesh has a skin) and its per-vertex `GetJoints()` (`Vector4u`) and `GetWeights()` (`Vector4`), empty for a static mesh, which the catalog's `MeshView` passes to the renderer as `joints` and `weights`. `AnimatorComponent` (reflected and saved: `Clip`, `Speed`, `Loop`, `PlayOnStart`, `CrossfadeTime`; runtime only: `Started`, `Playing`, `CurrentClip`, `Time`, `PreviousClip`/`PreviousTime`/`FadeElapsed`, `WarnedClip`, `PreviewTime` and `Palette`, one skinning matrix per joint) is registered with its serializer; the editor's Add Component menu adds it and the inspector shows its reflected fields. `AnimationSystem : ECS::System` (Animator + Mesh) overrides no play-mode event: play-mode events run in registration order and the application registers `ScriptSystem` after the engine's systems, so `EngineContext::UpdateAnimation(dt)` (public) calls its `Update(ecs, meshes, playing, dt)` right after `UpdatePlayMode`, before Transform, and a clip a script sets in OnUpdate shows that frame. While Playing it advances by the frame's scaled dt (Paused holds; dt 0): the first frame starts the animator (playing `Clip` at time 0 when `PlayOnStart`), a changed `Clip` plays the new clip from 0 and fades out of the old one from where it was over `CrossfadeTime` (none when 0 or nothing played), time advances by dt * `Speed`, looping or clamped by `Loop`. In Edit it shows `Clip` at `PreviewTime` when set, else the bind pose, and clears the play state. An unknown clip name shows the bind pose and warns once (`[Animation] Entity <id> has no clip '<name>' ...`); a mesh with no skeleton gets an empty palette. For code and scripts, `AnimationSystem::Play(ecs, meshes, entity, clip, fade?)` plays a clip of the entity's mesh from its start, crossfading over `fade` (stored as the runtime `RequestedFade`; the switch's length is kept in `FadeDuration`, so the saved `CrossfadeTime` is untouched) and restarting it when it is already the current clip; a clip the mesh does not have logs `[Animation] Entity <id> has no clip '<name>' on its mesh; keeping '<current>'.` and changes nothing. `Stop(ecs, entity)` clears `Clip` and the play state, so the bind pose shows, and `GetClipNames` lists the mesh's clips in file order. A non-looping clip that reaches its end sets the runtime `Finished` and publishes `AnimationFinishedEvent { Entity, Clip }` (`api/Events/AnimationEvents.hpp`) on the engine's `EventBus`, which `Update` now takes, once per play-through. Scratch poses are system members, so steady-state evaluation allocates nothing but a palette's first fill. **Game UI components** (epic HE-159; saved and loaded, in the editor's Add Component menu and inspector (reflected fields, an RGBA colour as a ColorEdit4), drawn by the game view's GameUi pass): `UiCanvasComponent` (`Enabled`, `ScaleMode` `UiCanvasScaleMode` ConstantPixelSize or ScaleWithTargetSize (the default), `ReferenceResolution` 1920x1080, `MatchWidthOrHeight` 0.5, `SortOrder`), the root of a UI tree drawn over the game view; `UiRectComponent` (`Visible`, `AnchorMin`/`AnchorMax`/`Pivot` default (0.5, 0.5), `Offset`, `Size` 100x100: HedgehogUI's `RectTransform`), which makes a child of a canvas or of another element an element; `UiImageComponent` (`Texture` under `assets://`, empty for a solid fill, and RGBA `Color`); `UiTextComponent` (`Text`, `Font` (a `.ttf`/`.otf` under `assets://`), `FontSize` 24 in canvas units, `Color`, `Align` `UiTextAlign`, `VerticalAlign` `UiTextVerticalAlign`, `Wrap`); `UiButtonComponent` (`Interactable`, `NormalTint`/`HoverTint`/`PressedTint`/`DisabledTint`, and the runtime `State` `UiButtonState` Normal/Hovered/Pressed). The components mirror HedgehogUI's enums rather than include it. `UiSystem : ECS::System` (signature `UiCanvasComponent`, `EngineContext::GetUiSystem`) is the entity view of canvases. The ECS now has 15 of its 16 component types (`MAX_COMPONENTS`), the audio components included. **Fonts** are catalog resources: `ResourceCatalog::GetFontContainer()` is a `FontContainer` (`api/Containers/FontContainer.hpp`) keyed by (path, pixel size), whose `FindOrBake(path, pixelSize)` bakes a font with ContentLoader's `LoadFont` on first use (the path under `assets://`, prefix optional, either slash) and returns the same index for every later use, so texts with one font and size share one atlas; a font that does not load logs once and is never retried, and fonts are never unloaded. `IResourceCatalog` (HedgehogCommon) gains `GetFontCount()` and `GetFontAtlas(index)` (`FontAtlasView`: width, height and the R8 coverage bytes) for the renderer; its overrides are not exported, so call them through the interface. **Input actions:** `EngineContext` loads `INPUT_ACTIONS_PATH` (`assets://Input/actions.yaml`) at construction (a missing file logs an info line, a broken one its error, and both use `MakeDefaultInputActions()`), watches it, and `UpdateContext` calls `ReloadInputActions(steady_clock::now())`, which re-reads a saved file at most once a second and resets the game action state. `UpdateGameInput(const HW::RawInput&)` evaluates the `Game` map into the game `ActionState` while Playing and resets it in Edit and Paused; `Play`, `Pause` and `Stop` reset it too, so a key held into Play presses on Play's first frame and nothing outside Play sees an action. The Editor (`Application::StepFrame`, right after polling) hands it `MakeGameInput` of the window's raw input over `EditorGui::GetGameInputRegion()`, the Game tab's image as of the last frame (pointer while the image is hovered; keyboard while the panel has focus, gained by a press on the image and lost by any press elsewhere or by hiding the tab, and ImGui wants no text input), with the gate kept in `EditorApplication`; `--game-mode` hands it the whole window (window size to framebuffer pixels, the ones the UI is extracted at, both enabled); tests call it directly. `GetInputActions()`, and `GetGameActionState()` const and non-const, so a system that handles an action (the game UI) can consume it, right after `UpdateGameInput` and before `UpdatePlayMode`. The editor camera: `UpdateEditorInput(const HW::RawInput&)` evaluates the `Editor` map in every play state (reset with the game state on a reload), and `UpdateContext` moves the flycam from it: `EditorCameraForward` along world x, `-EditorCameraRight` along y and `EditorCameraUp` along z at the camera's speed, and `EditorCameraLookX/Y` turning it only while `EditorCameraLookHold` is down (deltas are per frame, so a still pointer never turns it). The Editor hands it `MakeGameInput` over `EditorGui::GetSceneInputRegion()` (the Scene tab's image at one pixel per window pixel; pointer while hovered, a drag that began on it keeping its button through its own gate; keyboard while the scene panel has focus, by the Game tab's press rule, and no text field is edited, so typing in the inspector no longer moves the camera); `--game-mode` never calls it, so its camera stays still. **Audio:** `EngineContext` owns an `HA::AudioEngine` (`GetAudioEngine()`, declared before the ECS so it outlives the sounds) but never starts it: the Editor (`Application::Init`) and `--game-mode` call `Init` with a device, tests with `NoDevice`, and until then nothing plays. `AudioSourceComponent` (reflected and saved: `Clip` (under `assets://`, prefix optional, either slash), `Volume` (a slider, 0 to 1), `Pitch`, `Loop`, `PlayOnStart` (true), `Spatial` (true), `MinDistance` 1, `MaxDistance` 100; runtime only: `Sound`, an `HA::SoundHandle`) and `AudioListenerComponent` (`Active`) are registered with their serializers, in the editor's Add Component menu and its inspector. `AudioSystem : ECS::System` (`api/ECS/systems/AudioSystem.hpp`, signature `AudioSourceComponent` + `TransformComponent`, built with the ECS, the audio engine and the file system) plays in Play mode only: `OnPlayStart` starts every `PlayOnStart` source with a clip, `OnPlayPause`/`OnPlayResume` pause and resume their sounds, `OnPlayStop` stops every sound and clears the handles; removing a source (its removal callback, cleared in the destructor) stops its sound. `Play(ecs, entity)` restarts one source's sound. `Update(ecs, listeners, cameras)`, which `UpdateContext` calls after Light, sets the listener's pose (`MakeAudioPose` of the first active `AudioListenerComponent` by entity id, from `AudioListenerSystem`, the entity view of listeners with a Transform; else the enabled camera with the highest priority, then the lowest id; else the origin looking down -Z), each playing source's position, volume and pitch from its component, then has the engine reclaim finished sounds and clears their components' handles. `Assets/Audio/Tone440.wav` is a 0.5 s 440 Hz tone (220 whole cycles, so it loops cleanly) for trying it. `Assets/Models/Animated/TwoBoneStrip.gltf` is a two-joint test strip (Root, Tip one unit up; clips Bend, Tip 45 to 90 degrees about z over 1 s, and Lift, Root up 0 to 1 over 2 s) |
| `RHI` | static lib | Graphics abstraction: `IRHIDevice`, `IRHICommandList`, `IRHITexture`, … — dynamic rendering and `Barrier()` only (no render-pass/framebuffer objects); Vulkan backend under `src/Vulkan/`, native handles for integrations in `api/Vulkan/VulkanNative.hpp` |
| `RHIImGui` | static lib | ImGui's GPU renderer on the RHI (`RHIImGui::IGuiRenderer`), used only by the Editor |
| `HedgehogRenderer` | static lib | Multi-pass Vulkan renderer (see structure and passes below) |
| `ECS` | DLL | Entity Component System (EntityManager, ComponentManager, SystemManager, Coordinator). `ECS::System` has a virtual destructor and six play-mode events, each a no-op unless overridden: `OnPlayStart(ECS&)`, `OnPlayPause(ECS&)`, `OnPlayResume(ECS&)`, `OnPlayStop(ECS&)`, `OnFixedUpdate(ECS&, fixedDt)` and `OnUpdate(ECS&, dt)`; a system's own per-frame methods (Transform, Hierarchy, …) are separate and run in every mode. The ECS only forwards the events: `NotifyPlayStart`, `NotifyPlayPause`, `NotifyPlayResume`, `RunFixedUpdate(dt)` and `RunUpdate(dt)` visit every system in registration order, and `NotifyPlayStop` in reverse. The ECS keeps no play state and checks nothing; whoever drives play mode (the engine) owns the state, the clock and the scene snapshot, and decides when each event is due. `RegisterSystem<T>(args...)` forwards constructor arguments, systems keep registration order (`SystemManager::ForEachSystem`/`ForEachSystemReverse`), and `~ECS` destroys systems before component storage, so a system may clear its removal callback from its destructor; the ECS is movable, not copyable. `SetComponentRemovedCallback<T>(fn(Entity, T&))`: one callback per component type (a new one replaces the old, an empty one clears it; `GetComponentRemovedCallback<T>()` returns the current one, so a system can chain it and put it back), fired before the data goes, from `RemoveComponent<T>` and from `DestroyEntity`; `DestroyEntity` runs every array's callback before removing any component and releases the id last, so a callback sees all of the entity's components and `IsAlive` is still true. Entity generations: `IsAlive(e)` and `GetGeneration(e)`, bumped on destroy so a stale id+generation pair is detectable; destroying twice asserts. `SetSystemSignature<T>` backfills live entities that already match |

### HedgehogRenderer Structure

The renderer follows a strict `api` / `src` split:

```
HedgehogRenderer/
├── api/
│   └── HedgehogRenderer/
│       └── Renderer.hpp          ← sole public header
└── src/
    ├── Renderer/Renderer.cpp
    ├── RHIContext/               ← owns IRHIDevice + IRHISwapchain
    ├── Renderer/FrameRenderer    ← the frame: per-frame command lists, fences and semaphores,
    │                               views, shared phase, per-view graphs, present
    ├── Graph/                    ← the render graph, graph assets, engine pass types
    │   └── Passes/               ← one .hpp/.cpp per engine pass type, plus PassCommon
    ├── GraphPasses/              ← GraphPassServices: pipelines and uniform rings for the passes
    ├── Views/, Targets/, Frame/  ← ViewManager and culling, RenderTargetRegistry, SharedPhase
    ├── ResourceRegistry/         ← mesh/material GPU buffers and descriptor sets
    └── Pipeline/, Profiling/     ← .shader/.pl loading; FrameStats and Tracy zones
```

`api/` is the public include root (added to dependents' include paths).  
`src/` is private — never included from outside the module.

### Rendering a frame (HedgehogRenderer)

Every frame goes through the render graph: the Editor (and `--game-mode`) builds a `Renderer`, simulates, extracts a `RenderScene`, calls `SyncResources`, then `Renderer::RenderFrame`, which owns the frame lifecycle inline (fence wait, resize before acquire, shared phase, per-view graphs, one execute, present) in `src/Renderer/FrameRenderer`. The editor has three views (RENDERING.md section 7): **scene** (the flycam into the `scene` target), **game** (the scene's camera, redirected to the `game` target with `SetCameraTargetOverride`), and **result** (no camera; the `result` graph's `Ui` pass draws the editor into `main`, sampling both panel targets). A hidden panel tab is sized 0x0, so its view is dropped and its passes never declared (`GetLastFramePassCount`).

Graph passes (`assets/Graphs/*.graph`; each pass type is one `.hpp`/`.cpp` pair in `src/Graph/Passes/` exposing `Get<Name>PassType()`, its slots, parameters and build function, and `EnginePassTypes` registers them): the shared phase's **Shadow** (the cascaded shadow atlas, once per frame), then per view **DepthPrepass** → **Forward** (lit, samples the atlas) → **Gizmo** (scene view only: editor-layer bounds) or **GameUi** (game view only), and the result view's **Ui** (the application's `UiCallback` into `main`). **Game UI:** `Renderer::RenderFrame` first has the registry load the frame's `RenderScene::UiTextures` (`ResourceRegistry::SyncUiTextures`: each path's texture through the shared texture cache, magenta when missing, and a set in the GameUi shader's set-0 layout sampled clamped to the edge, at most `MAX_UI_TEXTURE_SETS` (256) with one warning past it, plus a 1x1 white set for solid fills; the layout comes from `GraphPassServices::ProvideUiTextureLayout`), and `Renderer::SyncResources` uploads every font the catalog baked since the last frame (`ResourceRegistry::SyncFonts`: the R8 atlas expanded to white with the coverage in alpha, so text needs no shader of its own, one set each in the same pool, at most `MAX_UI_FONT_SETS` (64) with one warning past it). `FrameRenderer::FillUiFrame` uploads `RenderScene::Ui` once per frame into a per-frame-in-flight vertex and 16-bit index buffer (`GraphPassServices::UploadUiGeometry`, grown on demand from `MIN_UI_VERTEX_CAPACITY`/`MIN_UI_INDEX_CAPACITY`) and fills `GraphFrameData::UiCommands`, `UiVertices`, `UiIndices`, `UiTextureSets` (per `UiTextures` entry, null when not loaded), `UiFontSets` (per `UiFonts` entry, null past the budget), `UiSolidTexture` and `UiTargetSize` for every view. The `GameUi` pass (`src/Graph/Passes/GameUiPass`, slot `color`, after Forward in `game.graph`, not in `scene.graph`) loads the colour, binds `EnginePipeline::GameUi` (`GameUi.shader`: `GameUi.pl` (set 0, one texture; 16-byte push constants), `Ui.vdes` (one interleaved 20-byte stream: position and UV as `r32g32_float`, colour as `r8g8b8a8_unorm`, a format `VertexDescLoader` now reads), alpha blending, no depth test and no depth attachment), pushes `MakeGameUiPushConstants(UiTargetSize)` (pixels, y down, onto clip space, so a UI laid out for one size stretches over the colour target it draws into) and records each command as a scissor (`MakeGameUiScissor`: scaled to the colour target, rounded outward, clamped, the command skipped when empty), its texture (its font's set for a `UI_FONT_TEXTURE` command, which is skipped when the font has none; the white set for `UI_NO_TEXTURE` or a texture that did not load) and one `DrawIndexed`. A frame without commands, geometry or the white set records nothing. `GameUi/Quad.vert` decodes the vertex colour from sRGB, as the pickers and textures are, and the fragment shader multiplies it by the texture. Views are culled by layer mask and frustum, and `CullViewInstances` splits a view's opaque instances into rigid (`GraphFrameData::OpaqueInstances`) and skinned (`SkinnedInstances`, `RenderInstance::JointCount > 0`). **Skinned meshes:** the frame uploads `RenderScene::JointMatrices` once (`GraphPassServices::UploadJointPalette`: a storage buffer per frame in flight, at least `MIN_PALETTE_CAPACITY` matrices and grown on demand, handed to the passes as `GraphFrameData::JointPalette`). DepthPrepass and Forward record the rigid instances exactly as before, then, when the view has skinned instances, the palette and the skinning streams (`CanDrawSkinned`), bind the skinned pipeline (`EnginePipeline::DepthPrepassSkinned`, `ForwardSkinned` or `ForwardSkinnedDoubleSided`; `DepthPrepassSkinned.shader`/`GraphForwardSkinned.shader` over `SkinnedPositionOnly.vdes`/`SkinnedFullMesh.vdes`, which add joints as `r32g32b32a32_uint` (`RHI::Format::R32G32B32A32Uint`) and weights as `r32g32b32a32_float`), bind every set again (its push-constant range differs, so the layouts are incompatible) with the palette at set 1 (depth) or set 3 (forward), and draw each with a 68-byte `SkinnedPushConstants` (the model matrix, then `PaletteOffset`). The vertex shaders blend four palette matrices through `Shaders/Common/Skinning.glsl` (`PALETTE_SET` picks the set). The shared Shadow pass casts them posed too: `SharedPhase` splits the casters (chosen by `ShadowCasterMask`) into rigid and skinned (`JointCount > 0`) from either of the shadow frame's lists (FrameRenderer hands it every scene instance in `OpaqueInstances`), and the pass draws every cascade's rigid casters as before, then binds `EnginePipeline::ShadowSkinned` once (`ShadowmapPassSkinned.shader`, the skinned depth prepass's layout and vertex shader with the shadow pass's `less_or_equal` depth test), the palette at set 1, and draws the skinned casters into each cascade again with that cascade's viewProj set. The forward shader does not sample the shadow atlas yet, so no shadow is visible on screen for any mesh.

The legacy fixed-pass renderer is gone: `DrawFrame`, every legacy pass, `RenderQueue` and `ResourceManager` with its textures. Render order comes from the graph compiler's topological sort, render targets are either pooled graph transients or view-owned targets in the render-target registry, the `Renderer` owns the mesh/material `ResourceRegistry` directly (its vertex streams are positions, UVs, normals and, aligned with the positions, the skinning streams: joint indices as `uint4` and weights as `float4`, zero for a static mesh, packed by the free function `AppendSkinningStreams` in `src/ResourceRegistry/SkinningStreams` and handed to the passes as `GraphFrameData::Joints`/`Weights`; no pass reads them yet), and `FrameRenderer` owns the per-frame command lists and synchronization objects. `Renderer.hpp`'s public surface is `RenderFrame`, `SyncResources`, `Cleanup`, the frame-stats pair and the view accessors (`CreateView`/`UpdateView`/`DestroyView`, `SetCameraTargetOverride`, `DeclareTarget`/`ResizeTarget`/`GetTargetTexture`, `GetLastFramePassCount`) and, for tools, the graph assets and pass types (`GetGraphNames`, `FindGraphAsset`, `GetGraphFile`, `FindPassType`, `GetPassTypeNames`, `GetGraphError`, `DiagnoseGraph`). The Editor's render graph editor (`Editor/Tools/RenderGraphEditor/`) draws and edits a graph with them: its edits are plain `GraphAsset` operations in `GraphEditing`, it checks every edit with `DiagnoseGraph` (problems in red on their node, and in a list under the canvas), it saves through `GraphAssetWriter` and the renderer hot-reloads the file, and node positions live in a `<name>.graph.layout` file beside the graph. New starts an empty untitled graph, Open... and Save As... pick any `.graph` file (`DialogueWindows::RenderGraphOpenDialogue`/`RenderGraphSaveDialogue`), and a picked file is named by `MakeGraphReference` (`Tools/RenderGraphEditor/GraphFileReference`): an engine graph's name, else a virtual path under the most specific mount, else an absolute path, normalized as the renderer lists it, and registered with `Renderer::LoadGraph`. The camera inspector (`EditorGui::DrawCameraGraph`) names the same references: its drop-down shows engine graphs by name and files by file name, Browse... picks a file through the same dialogue and `MakeGraphReference`, Edit opens the camera's graph with `RenderGraphEditorWindow::OpenGraph`, and a reference with no usable graph shows in red with the renderer's reason.

**ImGui belongs to the Editor, never the renderer.** `Editor/ImGuiLayer` owns the context, the GLFW platform backend and the GUI renderer (`RHIImGui::IGuiRenderer`, ImGui's Vulkan backend with dynamic rendering into any texture of one colour format, created in the `Renderer`'s `DeviceReadyCallback`, which hands the application the device and the swapchain's format once at construction). The result view's `Ui` pass hands the editor its colour target through a `UiCallback`. Neither `HedgehogRenderer` nor `RHI` has an ImGui include path or link, and the boundary check keeps it that way.
