# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Workflow

**Every change starts as a Jira ticket in project `HE` and lands as one pull request under ~1000 changed lines.** Read `WORKFLOW.md` before starting any work — it defines the ticket model, the sizing rule, branch and commit conventions, and the Jira/GitHub automation.

The short form:
- Branch `HE-<n>-<slug>` off `master`; no long-lived integration branches.
- Commit subjects and PR titles start `HE-<n>: `. A `commit-msg` hook and the `ticket-check` CI job enforce this; Jira uses it to move the ticket to **In Review** on PR creation and **Done** on merge.
- Break a problem into tickets with `/jira-tickets <problem>` before writing code.

## Build System

HedgehogEngine uses **Premake5** to generate Visual Studio 2022 solution files. There is no CMake.

**Initial setup** (run once, or after submodule changes):
```bat
Scripts\SetupWindows.bat
```
This initializes git submodules recursively and generates `HedgehogEngine.sln`.

**Building (CLI — always build after code changes, a change is not done until it compiles):**
```
Scripts\Build.bat [Debug|Release]        (default: Debug; locates MSBuild via vswhere)
```
**Build + run all tests in one step:**
```
Scripts\RunTests.bat [Debug|Release]     (exits nonzero if the build or any test fails)
```
Alternatively invoke MSBuild directly (`MSBuild.exe HedgehogEngine.sln /p:Configuration=Debug /p:Platform=x64 /m /v:m`) or open `HedgehogEngine.sln` in Visual Studio 2022. Configurations: `Debug` and `Release`, platform: `x64`.

**Shader compilation** is automatic via a Shaders project pre-build command that calls `ThirdParty/glslc/CompileShaders.bat`, compiling `.vert`/`.frag`/`.comp` GLSL sources to SPIR-V (`.spv`).

**Build output:** every executable and DLL of a configuration goes to one directory, `Binaries/windows-x86_64/[Debug|Release]/`, so each program finds its DLLs next to it with no copy step. Static libraries and object files go to `Binaries/Intermediates/windows-x86_64/[Debug|Release]/[ProjectName]/`. The two directories are `BinariesDir` and `IntermediatesDir` in the root `Build.lua`.

**Running tests** (doctest; each exe exits nonzero on failure):
```
Binaries/windows-x86_64/Debug/HedgehogMathTest.exe
Binaries/windows-x86_64/Debug/FileSystemTest.exe
Binaries/windows-x86_64/Debug/ECSTest.exe
Binaries/windows-x86_64/Debug/EcsSerializationTest.exe
Binaries/windows-x86_64/Debug/ContentLoaderTest.exe
Binaries/windows-x86_64/Debug/HedgehogExtractTest.exe
Binaries/windows-x86_64/Debug/RenderGraphTest.exe
Binaries/windows-x86_64/Debug/HedgehogEngineTest.exe
Binaries/windows-x86_64/Debug/ScriptingTest.exe
Binaries/windows-x86_64/Debug/AnimationTest.exe
Binaries/windows-x86_64/Debug/UiTest.exe
Binaries/windows-x86_64/Debug/HedgehogWindowTest.exe
Binaries/windows-x86_64/Debug/InputTest.exe
Binaries/windows-x86_64/Debug/AudioTest.exe
Binaries/windows-x86_64/Debug/EditorTest.exe
Binaries/windows-x86_64/Debug/HedgehogSettingsTest.exe
Binaries/windows-x86_64/Debug/CookerTest.exe
Binaries/windows-x86_64/Debug/LuaDebugTest.exe
```

**Renderer smoke test** — after any renderer/RHI change, run (from the repo root, needs a Vulkan GPU):
```
Binaries\windows-x86_64\Debug\Editor.exe --smoke-test [frames]
```
Renders N frames (default 120) and exits nonzero if any Vulkan validation error occurred (Debug builds enable `VK_LAYER_KHRONOS_validation`; messages route through Logger, counters live in `RHI/api/RHIDiagnostics.hpp` and are re-exported via `Renderer.hpp`).

**Game mode** — the render-graph path as a game build runs it, with no editor (a thin caller of HedgehogRuntime's `GameRuntime`, the game loop itself):
```
Binaries\windows-x86_64\Debug\Editor.exe --game-mode [frames] [scene.yaml]
```
Loads the named file under `Assets/Scenes/`, else the project's startup scene (`Project.yaml`'s `startup_scene`), else `Assets/Scenes/Default.yaml` (named files, e.g. `Animated.yaml`, two animated `TwoBoneStrip`s and a rigid cube, for skinned rendering, or `Hud.yaml`, a cube under a game UI canvas: a translucent top bar with a logo and a title, a health bar with its value and a tinted textured button labelled PLAY, the text in `Assets/Fonts/Karla-Regular.ttf`, SIL OFL 1.1), builds a `Renderer` exactly as the editor does, but creates no ImGui, and renders N frames (default 120) with `RenderFrame` from views derived from the scene's camera components. Exits nonzero on any Vulkan validation error **or if an ImGui context ever exists** — the renderer not depending on ImGui is checked, not assumed. Run it after any render-graph or renderer change, alongside `--smoke-test`; like it, it needs a GPU and runs locally only.

**Game executable** — the project as a player runs it (`Game/`, a console in Debug and a plain window in Release, linking no ImGui):
```
Binaries\windows-x86_64\Debug\Game.exe [--frames N] [--project <folder or Project.yaml>]
```
Plays the project's startup scene through HedgehogRuntime's `GameRuntime` (`UseProjectWindow`: the window's title, size and fullscreen come from `Project.yaml`; vsync is stored but not applied yet) until the window closes or N frames have run. The project is the nearest `Project.yaml` above the executable (`FS::GetEngineRootDirectory`, so it runs from any working directory), or the one `--project` names (through `FS::SetEngineRootDirectory`; a path with no `Project.yaml` exits 1). Exits nonzero when the game does not start or on any Vulkan validation error (counted after teardown).

**Lua debugger** — VS Code attaches to the scripts of the running editor (in Play), `--game-mode` or `Game.exe` when `engine_settings.yaml` has `lua_debugger: { enabled: true, port: 4711 }` (off by default: nothing is created, no thread, socket or hook). Install `Tools/VSCode/hedgehog-lua-debug` (its README: **Developer: Install Extension from Location...**, and an `attach` configuration of type `hedgehog-lua`); `python Tools/VSCode/hedgehog-lua-debug/dap_check.py <script.lua> <line>` drives the same session without VS Code (attach, break, stack, locals, one step, continue, detach; nonzero on failure). While a script is stopped the frame waits inside it: the window polls its events and its title ends with " - Paused in debugger".

**Cooker** — packages a project's assets (`Tools/Cooker/`, a console tool linking HedgehogEngine, HedgehogSettings, EcsSerialization, FileSystem and Logger):
```
Binaries\windows-x86_64\Debug\Cooker.exe --project <folder> --out <folder> [--scene <assets://...yaml>]... [--glslc <glslc.exe>]
```
The project is the folder holding `Project.yaml`. It first compiles every engine shader source whose `.spv` is missing or older (`<project>/HedgehogEngine/HedgehogRenderer/assets/Shaders`, with `<project>/ThirdParty/glslc/glslc.exe` unless `--glslc` names one; a project without the sources or glslc is packaged as last compiled, with a warning), then builds a cook plan (`CookPlan.hpp`, `Cooker` namespace: `BuildCookPlan(projectRoot, extraScenes)`: the `AssetDependencyCollector` closure of the startup scene, each `--scene`, and HedgehogEngine's `GetEngineRuntimeAssets()` (the project, the settings and input actions when present, the default cube, sphere and cells texture, and the shipped `scene`, `game` and `result` graphs with their shaders); a missing reference, `<path> (referenced by <asset>) does not exist.`, a project without a startup scene and a path outside `engine://`/`assets://` are errors) and copies it (`CookPackage`) into the package laid out as `EngineContext::InitFileSystem` mounts it: `engine://X` at `<out>/X`, `assets://X` at `<out>/Assets/X` (`ToPackagePath`, which refuses a `..` leaving its mount). `<out>/manifest.yaml` (`version: 1`, then each file's `path`, `size` and FNV-1a 64 `hash`) makes a second cook copy only files whose source changed or whose copy is gone, and remove files the project no longer references, so the package holds the closure and nothing else. Any error prints each message and exits 1 before anything is copied. `Game.exe --project <out>` plays the package.

**Packaging a game** — one command builds the playable folder `Build\<ProjectName>\` (`Project.yaml`'s `name`; `Build/` is gitignored):
```
Scripts\PackageGame.bat
```
It builds Release (`Build.bat`), cooks the project into the folder with the Cooker (incremental, so a repackage copies only what changed), copies `Game.exe` and the DLLs it loads (`glfw`, `Logger`, `FileSystem`, `HedgehogMath`, `HedgehogCommon`, `ECS`, `EcsSerialization`, `ContentLoader`, `HedgehogSettings`, `HedgehogWindow`, `HedgehogAudio`, `HedgehogEngine`; a new DLL the game links must be added to its list), fails if the folder holds an editor, Cooker or test executable, a `.pdb`, `.ilk` or `.lib`, `DialogueWindows.dll`, anything named `imgui` or a GLSL source, then copies the folder to `%TEMP%` and runs `Game.exe --frames 120` there (`start /wait`, the Release game being a windowed app), failing on a nonzero exit. The folder runs on a machine with only the Vulkan runtime and the VC++ redistributable; saves go to the player's LocalAppData as usual.

**Regenerating solution** after modifying any `Build.lua` files:
```
Vendor\Binaries\Premake\Windows\premake5.exe --file=Build.lua vs2022
```

**CI:** `.github/workflows/ticket-check.yml` fails any PR whose title carries no `HE-<number>` key, and `module-boundaries.yml` runs `Scripts\CheckModuleBoundaries.ps1` and its `-SelfTest` (see *Architecture*). There is currently **no build workflow** — Debug/Release builds and the test exes must be run locally before opening a PR (the smoke test is local-only in any case: CI runners have no Vulkan GPU).

## Performance

- **Frame budget: 16.6 ms (60 FPS) in Release** at default window size on the baseline machine. Weigh this in any plan touching the frame loop, render passes, ECS iteration, or per-frame allocations.
- **No optimization without a before/after number.** Measure with:
  ```
  Binaries\windows-x86_64\Release\Editor.exe --benchmark [frames] [scene.yaml]
  ```
  It loads `Assets/Scenes/benchmark.yaml` (or the named file under `Assets/Scenes/`, e.g. `Default.yaml`), warms up 120 frames, measures 600, and logs CPU timings (avg/min/max/p95) for `RenderFrame(total)` and each render-graph pass (summed over the views that ran it) plus wall frame time and FPS. Always Release; run before and after the change and quote both numbers. Baseline table and methodology: `PERFORMANCE.md`.
- Per-pass rows are CPU record times (barriers plus the pass's closure, `RenderGraphRuntime::GetLastPassTimings`); GPU-bound waiting shows up in `RenderFrame(total)`, which includes the fence wait, acquire, submit and present. For GPU-side detail, connect the Tracy 0.13.1 server (client is linked in Release, `TRACY_ON_DEMAND`); zones via `HH_PROFILE_ZONE` in `HedgehogRenderer/src/Profiling/Profiler.hpp`.

## Architecture

The engine is a set of C++20 libraries (mix of static and shared) with an `Editor` executable as the entry point. Dependencies flow strictly upward:

```
Game (ConsoleApp / WindowedApp) the player's executable: HedgehogRuntime and what it links, no ImGui
Cooker (ConsoleApp, Tools/)     packages a project: HedgehogEngine, HedgehogSettings, EcsSerialization, FileSystem
Editor (ConsoleApp)            owns ImGui: context, GLFW backend, GUI renderer (RHIImGui)
  └── HedgehogRuntime + HedgehogEngine + HedgehogExtract + HedgehogScripting + HedgehogRenderer + RHIImGui
      + HedgehogWindow + HedgehogSettings + HedgehogCommon + DialogueWindows + ECS + FileSystem
      + Logger + Lua + imgui
        ├── HedgehogRuntime  (static lib) → HedgehogEngine, HedgehogExtract, HedgehogScripting,
        │                                   HedgehogRenderer, HedgehogInput, HedgehogAudio, HedgehogSettings,
        │                                   HedgehogWindow, FileSystem, Logger — never ImGui; the
        │                                   editor-free game loop, run by --game-mode
        ├── HedgehogLuaDebug (static lib) → Logger, Lua, ws2_32, nlohmann json (ThirdParty/tinygltf/json.hpp,
        │                                   src/ only); linked by HedgehogScripting (its ScriptDebugger)
        ├── HedgehogExtract  (static lib) → ECS, HedgehogEngine, HedgehogMath, HedgehogUI
        ├── HedgehogAnimation (static lib) → HedgehogMath (headers only: ContentLoader's loaded
        │                                   skin and clip structs); linked by HedgehogEngine
        ├── HedgehogInput    (static lib) → HedgehogMath, FileSystem, Logger, yaml-cpp (headers only:
        │                                   HedgehogWindow's RawInput and key codes); linked by
        │                                   HedgehogEngine
        ├── HedgehogAudio    (DLL)        → miniaudio (static C lib), HedgehogMath, FileSystem, Logger;
        │                                   linked by HedgehogEngine
        ├── HedgehogUI       (static lib) → HedgehogMath (headers only: HedgehogExtract's
        │                                   UiDrawList, ContentLoader's LoadedFont); linked by
        │                                   HedgehogExtract and HedgehogEngine
        ├── HedgehogScripting (static lib) → HedgehogEngine, HedgehogInput, HedgehogAudio, ECS, HedgehogMath, FileSystem, Logger,
        │                                   Lua, sol2 (header-only); registered by the Editor
        │                                   and --game-mode
        ├── HedgehogEngine   (DLL)        → HedgehogCommon, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, HedgehogAnimation, HedgehogInput, HedgehogAudio, HedgehogUI, HedgehogMath, ECS, EcsSerialization,
        │                                   FileSystem, yaml-cpp, Logger
        ├── HedgehogRenderer (static lib) → RHI, HedgehogMath, HedgehogSettings, HedgehogWindow,
        │                                   ContentLoader, FileSystem, Logger, yaml-cpp, Tracy
        │                                   (headers only: HedgehogCommon, HedgehogExtract's
        │                                   RenderScene; never the ECS, HedgehogEngine or ImGui)
        ├── RHIImGui         (static lib) → RHI, imgui (ImGui's Vulkan renderer, via
        │                                   RHI/api/Vulkan/VulkanNative.hpp)
        ├── HedgehogWindow   (DLL)        → HedgehogMath, GLFW, Logger
        ├── HedgehogSettings (DLL)        → FileSystem, yaml-cpp, Logger
        ├── HedgehogCommon   (DLL)        → HedgehogMath
        └── RHI              (static lib) → Vulkan (Volk + VMA), Logger — no ImGui
```

`Scripts\CheckModuleBoundaries.ps1` enforces four rules on `#include` strings: no include reaches into another module's `src/`; nothing under `HedgehogRenderer/` includes `ECS/`, the engine module (`HedgehogEngine/HedgehogEngine/`, `HedgehogEngine/api/`), `imgui.h` or `imgui_impl_*`; and nothing under `HedgehogEngine/HedgehogEngine/` (tests included) includes Lua (`Lua/...`, `lua.h`, `lualib.h`, `lauxlib.h`, `lua.hpp`), sol2 (`sol/...`) or `HedgehogScripting/...`, the scripting library above it; and nothing under `HedgehogRuntime/` or `Game/` includes `imgui.h` or `imgui_impl_*`, so the Game executable links no editor UI. Each include is reported once, however many patterns it matches. `-SelfTest` builds a throwaway tree shaped like the repository, plants one violation of each kind (a cross-module `src/` include, the renderer including the ECS and `imgui.h`, the engine including Lua (`ThirdParty/Lua/lua/lua.h`, `lauxlib.h`), `sol/` and `HedgehogScripting/`, the runtime including `imgui.h` and `backends/imgui_impl_glfw.h`, `Game` including `imgui.h`), checks each gives exactly one violation and that the tree passes without them (a `HedgehogScripting` module including sol2 and the `Editor` including `imgui.h` included), and lists each case it caught. `RunTests.bat` runs the check and then the self-test before building, and CI (`module-boundaries.yml`) runs both as separate steps.

**The renderer is being rewritten.** `RENDERING.md` at the repository root is the design: a camera-and-view architecture where a `CameraComponent` carries scene data, a `View` is the render request, and each view owns a render graph. Every frame now renders through it (see *Rendering a frame* below), and the legacy fixed-pass renderer is deleted. Epic [HE-63](https://viktoravoitovych.atlassian.net/browse/HE-63) lands it as 28 sub-1000-line pull requests.

### Key Modules

| Module | Type | Role |
|--------|------|------|
| `HedgehogMath` | DLL | Vectors, matrices, AABB/OBB/Plane/Frustum primitives; `Quaternion` (identity, axis-angle and Euler in degrees, multiply, rotate, normalize, inverse, `Slerp`, `ToMatrix`, `LookRotation` turning local -Z to forward with +Y up). `FromEuler(e).ToMatrix()` equals TransformSystem's `GetRotationX * GetRotationY * GetRotationZ`, so a `TransformComponent` keeps storing Euler degrees; `ToEuler` gives y in [-90, 90] and z = 0 at gimbal lock |
| `HedgehogCommon` | DLL | Shared renderer constants (`MAX_FRAMES_IN_FLIGHT`, `MAX_LIGHTS_COUNT`, …), Camera; `api/EngineRenderAssets.hpp`, where the renderer's own assets live (`ENGINE_GRAPH_DIRECTORY`, the engine shaders' virtual paths, and `PASS_TYPE_SHADERS`, the shaders each engine pass type draws with, `Shadow` for a graph importing the shadow atlas), read by the renderer and by the engine's asset dependency followers |
| `HedgehogWindow` | DLL | GLFW window wrapper, input handling (namespace `HW`). Input is one record, the complete `RawInput` (`api/RawInput.hpp`, pure data): every key (`api/InputCodes.hpp`: `Key`, valued as GLFW's codes, checked by `static_assert`s in Window.cpp, `KEY_COUNT` 349; `MouseButton`, 8), the cursor position (window coordinates, y down), the cursor and scroll deltas summed since the frame began, `CursorInside` and `Focused`. It is filled by GLFW-free exported free functions (`api/RawInputEvents.hpp`): `BeginInputFrame` zeroes the deltas (`WindowContext::HandleInput` calls `Window::BeginInputFrame` before polling), `ApplyKeyEvent` (a repeat counts as down; an unknown or out-of-range code is ignored), `ApplyMouseButtonEvent`, `ApplyCursorEvent` (the first event, and the first after the cursor leaves, sets the position without a delta), `ApplyScrollEvent` (summed), `ApplyCursorEnter`, `ApplyFocus` (losing focus releases every key and button) and `ApplyGamepadState(raw, connected, buttons, axes)` (the first gamepad: `RawInput::Gamepad` is a `GamepadState` of `Connected`, 15 `Buttons` (`GamepadButton`, GLFW's standard layout: A, B, X, Y, bumpers, Back, Start, Guide, thumbs, D-pad) and 6 `Axes` (`GamepadAxis`: sticks in [-1, 1], y down, so up is -1; triggers stored in [0, 1], 0 at rest, from GLFW's [-1, 1]); not connected zeroes it all). `Window::PollGamepad()` reads the first joystick GLFW maps as a gamepad, and `WindowContext::HandleInput` calls it after polling events. `Window::GetRawInput()` is never filtered: deciding what reaches the game or the editor camera is the application's job (HedgehogInput's `MakeGameInput`). The legacy `InputState`, `GetInputState` and `SetGuiCallback` are gone; F11 still toggles fullscreen. `Window::GetWindowSize` is the client area in the cursor's coordinates, beside `GetFramebufferSize`; `PollEvents()` handles pending events outside the frame loop (while a script is stopped in the debugger) and `GetTitle`/`SetTitle` read and change the title |
| `HedgehogSettings` | DLL | YAML-based engine configuration (`engine_settings.yaml`: shadow map and layer names; a `game:` section from before project settings is ignored and dropped on save) and, owned by `Settings` (`GetProjectSettings()`) but loaded and saved on its own, the project: `api/ProjectSettings.hpp`, `ProjectSettings` (`PATH` `engine://Project.yaml`, shipped at the repository root): `name` (`DEFAULT_NAME` HedgehogEngine; `IsValidName`: 1 to 64 of A-Z, a-z, 0-9, `_`, `-` and inner spaces, one plain folder name, which names the saves folder), `startup_scene` (empty, or a `.yaml` under `assets://` with no `..`, empty or drive segment, `IsValidStartupScene`; backslashes stored as slashes; the shipped one is `assets://Scenes/Default.yaml`), `window` (`title`, empty for the name; `width`/`height`, `DEFAULT_WINDOW_WIDTH`/`HEIGHT` 1366x768, clamped to `MIN_WINDOW_SIZE` 64 .. `MAX_WINDOW_SIZE` 16384; `fullscreen`; `vsync`, on; stored for the Game executable, which applies them) and `game_data_version` (at least 1, what saves carry and migrate to). `GetLuaDebuggerSettings()` is a plain `LuaDebuggerSettings` (`api/LuaDebuggerSettings.hpp`: `Enabled` false, `Port` `DEFAULT_PORT` 4711), engine_settings.yaml's `lua_debugger: { enabled, port }` (a port outside 1..65535 keeps the default with a warning), always written A refused value is logged (`[Project] ...`) and changes nothing; a setter that changes a value marks it dirty (`IsDirty`/`CleanDirtyState`). `Load` starts from the defaults (a missing key keeps its default, a refused value its default with a warning), returns false keeping the defaults for a missing file and keeping the settings as they were, with an error, for a malformed one; `Save` writes every key and cleans the dirty state |
| `HedgehogEngine` | DLL | Engine context; resource catalog (Material, Mesh, Texture containers); ECS systems and components; scenes (`SceneManager`: file load/save, and `CaptureSnapshot`/`RestoreSnapshot`, an in-memory `SceneSnapshot` of the YAML, scene name and game-object index; restore replaces the whole tree, brings entities back under their captured ids and runs the same post-load refresh as `LoadScene`; `GetScenePath` is the virtual path last loaded or saved, empty for a new scene; `CaptureWorld`/`RestoreWorld(node, sourceName)` do the same with a document node for a save's World section, the scene taking the document's name). **Save games** (`api/Save/SaveGameManager.hpp`, `EngineContext::GetSaveGames()`, epic HE-167): a save holds the world (section `World`) and every section another module registers (`RegisterSection(name, save, load)`; the script system registers `Scripts`), so the engine never depends on what is above it. `SetSaveDirectory` (the Editor uses `FS::GetSavesDirectory(<project name>, true)`, the editor folder, after loading `Project.yaml` in `Application::Init` (and again when File > Project Settings saves), and `--game-mode` the game folder; until set every request fails with an error), `GetGameDataVersion` (the project settings' `game_data_version`, read on every call; the manager takes the engine's `Settings`, built before it), `RegisterMigration(fromVersion, step)` (an `EcsSerialization::SaveMigrationStep` from that game data version to the next), `GetUnloadableReason(metadata)` (empty, or `the save is format version <n>, but this build reads versions 1 to <m>` / `the save is game data version <n>, but this game reads versions 1 to <m>`), `RequestSave(slot)` and `RequestLoad(slot)` (false, logged, for an invalid name, no directory or, for a load, a missing slot or one that cannot load, `[Save] Slot '<slot>' cannot be loaded: <reason>.`), `ListSlots`, `SlotExists`, `DeleteSlot` and `IsValidSlotName`. Requests wait for the end of the frame's gameplay: `UpdatePlayMode` calls `ProcessRequests` after the fixed steps and the update, so a save sees a consistent state and a load never runs under a script. Saves run first, in request order (metadata: the game data version, the scene path, an ISO 8601 UTC timestamp, the clock's `Time` as play time), then the last load requested: refused again if it cannot load, its sections migrated on the save's own copy by the registered C++ steps from its game data version to the current one (a failing step, `[Save] Slot '<slot>' cannot be loaded: migrating game data version <n> to <n + 1>: <why>.`, refuses the load before the world is touched; a migration logs `[Save] Slot '<slot>' migrated from game data version <n> to <m>.`), the world replaced by the saved one (whatever scene is open), each registered section handed its data and the saved game data version (`LoadSection(node, savedGameDataVersion)`), `[Save] Loaded slot '<slot>'.` and `GameLoadedEvent { Slot }` (`api/Events/SaveEvents.hpp`). `Stop` drops pending requests, and its restore of the pre-Play snapshot means a load in Play never reaches the edited scene. `Time/FixedStepClock`: a plain-data fixed-step clock (`FixedDeltaTime` 1/60, `MaxSubsteps` 8, `TimeScale`, plus accumulator, simulated `Time` and counters) with free functions `AdvanceFixedStepClock(clock, realDt)`, which returns the steps to run this frame (capped at `MaxSubsteps`, excess dropped; bad frame times count as zero; a small tolerance makes 1/30 s exactly two 1/60 s steps; bad settings fall back to the defaults), and `ResetFixedStepClock`, which keeps the settings. It has no pause flag: play mode simply stops advancing it. **Play mode** lives in `EngineContext` (`PlayState` Edit/Playing/Paused, the snapshot and the clock; the ECS only forwards events). `Play()` (from Edit) captures a snapshot, resets the clock and sends `NotifyPlayStart`; `Pause()`/`Resume()` send `NotifyPlayPause`/`NotifyPlayResume`; `Stop()` (from Playing or Paused) sends `NotifyPlayStop` (reverse order), then restores the snapshot; a call in the wrong state returns false and sends nothing. `UpdatePlayMode(dt)` (public, so tests drive frames headless) runs only while Playing: the clock's fixed steps of `RunFixedUpdate(FixedDeltaTime)`, then one `RunUpdate(dt * TimeScale)`. `UpdateContext(aspectRatio, dt)` (it needs no window; `Engine::UpdateContext(dt, aspect)` calls it) calls it before Transform, Hierarchy and Light, which run in every mode. `~EngineContext` sends `NotifyPlayStop` if still playing, without restoring. Scripts run in HedgehogScripting's `ScriptSystem`, which the application registers; the engine only stores `ScriptComponent` data (loading a scene runs no script code). The engine has no Lua of its own: it neither links nor includes Lua, and `ScriptComponent` is a pure-data struct (`Enable`, `ScriptPath`, `Properties`, an ordered `std::vector<ScriptProperty>`, and `Visit`). A `ScriptProperty` is `Name`, `ScriptPropertyType Type` (Number, Bool, Vector3, Color, String, EntityRef, AssetRef), `ScriptPropertyValue Value` (`std::variant<bool, float, HM::Vector3, std::string, ECS::Entity>`; Color is an RGB `Vector3`, AssetRef a path under `assets://`) and `AssetType` (the content type an AssetRef takes); free functions `FindScriptProperty` and `SetScriptProperty` find one by name and replace-or-append. **Asset dependencies:** `api/Assets/EngineAssetDependencies.hpp`'s `RegisterEngineAssetDependencies(collector)` registers with EcsSerialization's `AssetDependencyCollector` the AssetRef properties of Mesh, Render, AudioSource, UiImage, UiText and Camera (through `NormalizeGraphReference`: a bare name such as `game` is `<ENGINE_GRAPH_DIRECTORY>/game.graph`, anything else a path), `ScriptComponent` (its `ScriptFile`, the base `assets://Scripts/Base/ActorScript.lua` and its AssetRef properties' values) and the followers `.material` (`BaseColor`), `.graph` (its pass types' shaders from HedgehogCommon's `PASS_TYPE_SHADERS`, the shadow pass's when it imports), `.shader` (pipeline layout, vertex description and `.spv` stages, relative) and `.gltf` (external buffers and images, not `data:` URIs); a script's code is not read. `GetEngineRuntimeAssets()` lists what the engine and runtime load whatever the scene (`EngineRuntimeAsset { Path, Required }`: the project, the settings and `INPUT_ACTIONS_PATH` (not required), MeshSystem's default cube and sphere, MaterialContainer's cells texture and HedgehogCommon's `SHIPPED_GRAPHS`, which the renderer also checks at start), for the Cooker. ### HedgehogRenderer Structure

The renderer follows a strict `api` / `src` split:

```
HedgehogRenderer/
├── api/
│   └── HedgehogRenderer/
│       └── Renderer.hpp          ← sole public header
└── src/
    ├── Renderer/Renderer.cpp
    ├── RHIContext/               ← owns IRHIDevice + IRHISwapchain
    ├── Renderer/FrameRenderer    ← the frame: per-frame command lists, fences and semaphores,
    │                               views, shared phase, per-view graphs, present
    ├── Graph/                    ← the render graph, graph assets, engine pass types
    │   └── Passes/               ← one .hpp/.cpp per engine pass type, plus PassCommon
    ├── GraphPasses/              ← GraphPassServices: pipelines and uniform rings for the passes
    ├── Views/, Targets/, Frame/  ← ViewManager and culling, RenderTargetRegistry, SharedPhase
    ├── ResourceRegistry/         ← mesh/material GPU buffers and descriptor sets
    └── Pipeline/, Profiling/     ← .shader/.pl loading; FrameStats and Tracy zones
```

`api/` is the public include root (added to dependents' include paths).  
`src/` is private — never included from outside the module.

### Rendering a frame (HedgehogRenderer)

Every frame goes through the render graph: the Editor (and `--game-mode`) builds a `Renderer`, simulates, extracts a `RenderScene`, calls `SyncResources`, then `Renderer::RenderFrame`, which owns the frame lifecycle inline (fence wait, resize before acquire, shared phase, per-view graphs, one execute, present) in `src/Renderer/FrameRenderer`. The editor has three views (RENDERING.md section 7): **scene** (the flycam into the `scene` target), **game** (the scene's camera, redirected to the `game` target with `SetCameraTargetOverride`), and **result** (no camera; the `result` graph's `Ui` pass draws the editor into `main`, sampling both panel targets). A hidden panel tab is sized 0x0, so its view is dropped and its passes never declared (`GetLastFramePassCount`).

Graph passes (`assets/Graphs/*.graph`; each pass type is one `.hpp`/`.cpp` pair in `src/Graph/Passes/` exposing `Get<Name>PassType()`, its slots, parameters and build function, and `EnginePassTypes` registers them): the shared phase's **Shadow** (the cascaded shadow atlas, once per frame), then per view **DepthPrepass** → **Forward** (lit, samples the atlas) → **Gizmo** (scene view only: editor-layer bounds) or **GameUi** (game view only), and the result view's **Ui** (the application's `UiCallback` into `main`). **Game UI:** `Renderer::RenderFrame` first has the registry load the frame's `RenderScene::UiTextures` (`ResourceRegistry::SyncUiTextures`: each path's texture through the shared texture cache, magenta when missing, and a set in the GameUi shader's set-0 layout sampled clamped to the edge, at most `MAX_UI_TEXTURE_SETS` (256) with one warning past it, plus a 1x1 white set for solid fills; the layout comes from `GraphPassServices::ProvideUiTextureLayout`), and `Renderer::SyncResources` uploads every font the catalog baked since the last frame (`ResourceRegistry::SyncFonts`: the R8 atlas expanded to white with the coverage in alpha, so text needs no shader of its own, one set each in the same pool, at most `MAX_UI_FONT_SETS` (64) with one warning past it). `FrameRenderer::FillUiFrame` uploads `RenderScene::Ui` once per frame into a per-frame-in-flight vertex and 16-bit index buffer (`GraphPassServices::UploadUiGeometry`, grown on demand from `MIN_UI_VERTEX_CAPACITY`/`MIN_UI_INDEX_CAPACITY`) and fills `GraphFrameData::UiCommands`, `UiVertices`, `UiIndices`, `UiTextureSets` (per `UiTextures` entry, null when not loaded), `UiFontSets` (per `UiFonts` entry, null past the budget), `UiSolidTexture` and `UiTargetSize` for every view. The `GameUi` pass (`src/Graph/Passes/GameUiPass`, slot `color`, after Forward in `game.graph`, not in `scene.graph`) loads the colour, binds `EnginePipeline::GameUi` (`GameUi.shader`: `GameUi.pl` (set 0, one texture; 16-byte push constants), `Ui.vdes` (one interleaved 20-byte stream: position and UV as `r32g32_float`, colour as `r8g8b8a8_unorm`, a format `VertexDescLoader` now reads), alpha blending, no depth test and no depth attachment), pushes `MakeGameUiPushConstants(UiTargetSize)` (pixels, y down, onto clip space, so a UI laid out for one size stretches over the colour target it draws into) and records each command as a scissor (`MakeGameUiScissor`: scaled to the colour target, rounded outward, clamped, the command skipped when empty), its texture (its font's set for a `UI_FONT_TEXTURE` command, which is skipped when the font has none; the white set for `UI_NO_TEXTURE` or a texture that did not load) and one `DrawIndexed`. A frame without commands, geometry or the white set records nothing. `GameUi/Quad.vert` decodes the vertex colour from sRGB, as the pickers and textures are, and the fragment shader multiplies it by the texture. Views are culled by layer mask and frustum, and `CullViewInstances` splits a view's opaque instances into rigid (`GraphFrameData::OpaqueInstances`) and skinned (`SkinnedInstances`, `RenderInstance::JointCount > 0`). **Skinned meshes:** the frame uploads `RenderScene::JointMatrices` once (`GraphPassServices::UploadJointPalette`: a storage buffer per frame in flight, at least `MIN_PALETTE_CAPACITY` matrices and grown on demand, handed to the passes as `GraphFrameData::JointPalette`). DepthPrepass and Forward record the rigid instances exactly as before, then, when the view has skinned instances, the palette and the skinning streams (`CanDrawSkinned`), bind the skinned pipeline (`EnginePipeline::DepthPrepassSkinned`, `ForwardSkinned` or `ForwardSkinnedDoubleSided`; `DepthPrepassSkinned.shader`/`GraphForwardSkinned.shader` over `SkinnedPositionOnly.vdes`/`SkinnedFullMesh.vdes`, which add joints as `r32g32b32a32_uint` (`RHI::Format::R32G32B32A32Uint`) and weights as `r32g32b32a32_float`), bind every set again (its push-constant range differs, so the layouts are incompatible) with the palette at set 1 (depth) or set 3 (forward), and draw each with a 68-byte `SkinnedPushConstants` (the model matrix, then `PaletteOffset`). The vertex shaders blend four palette matrices through `Shaders/Common/Skinning.glsl` (`PALETTE_SET` picks the set). The shared Shadow pass casts them posed too: `SharedPhase` splits the casters (chosen by `ShadowCasterMask`) into rigid and skinned (`JointCount > 0`) from either of the shadow frame's lists (FrameRenderer hands it every scene instance in `OpaqueInstances`), and the pass draws every cascade's rigid casters as before, then binds `EnginePipeline::ShadowSkinned` once (`ShadowmapPassSkinned.shader`, the skinned depth prepass's layout and vertex shader with the shadow pass's `less_or_equal` depth test), the palette at set 1, and draws the skinned casters into each cascade again with that cascade's viewProj set. The forward shader does not sample the shadow atlas yet, so no shadow is visible on screen for any mesh.

The legacy fixed-pass renderer is gone: `DrawFrame`, every legacy pass, `RenderQueue` and `ResourceManager` with its textures. Render order comes from the graph compiler's topological sort, render targets are either pooled graph transients or view-owned targets in the render-target registry, the `Renderer` owns the mesh/material `ResourceRegistry` directly (its vertex streams are positions, UVs, normals and, aligned with the positions, the skinning streams: joint indices as `uint4` and weights as `float4`, zero for a static mesh, packed by the free function `AppendSkinningStreams` in `src/ResourceRegistry/SkinningStreams` and handed to the passes as `GraphFrameData::Joints`/`Weights`; no pass reads them yet), and `FrameRenderer` owns the per-frame command lists and synchronization objects. `Renderer.hpp`'s public surface is `RenderFrame`, `SyncResources`, `Cleanup`, the frame-stats pair and the view accessors (`CreateView`/`UpdateView`/`DestroyView`, `SetCameraTargetOverride`, `DeclareTarget`/`ResizeTarget`/`GetTargetTexture`, `GetLastFramePassCount`) and, for tools, the graph assets and pass types (`GetGraphNames`, `FindGraphAsset`, `GetGraphFile`, `FindPassType`, `GetPassTypeNames`, `GetGraphError`, `DiagnoseGraph`). The Editor's render graph editor (`Editor/Tools/RenderGraphEditor/`) draws and edits a graph with them: its edits are plain `GraphAsset` operations in `GraphEditing`, it checks every edit with `DiagnoseGraph` (problems in red on their node, and in a list under the canvas), it saves through `GraphAssetWriter` and the renderer hot-reloads the file, and node positions live in a `<name>.graph.layout` file beside the graph. New starts an empty untitled graph, Open... and Save As... pick any `.graph` file (`DialogueWindows::RenderGraphOpenDialogue`/`RenderGraphSaveDialogue`), and a picked file is named by `MakeGraphReference` (`Tools/RenderGraphEditor/GraphFileReference`): an engine graph's name, else a virtual path under the most specific mount, else an absolute path, normalized as the renderer lists it, and registered with `Renderer::LoadGraph`. The camera inspector (`EditorGui::DrawCameraGraph`) names the same references: its drop-down shows engine graphs by name and files by file name, Browse... picks a file through the same dialogue and `MakeGraphReference`, Edit opens the camera's graph with `RenderGraphEditorWindow::OpenGraph`, and a reference with no usable graph shows in red with the renderer's reason.

**ImGui belongs to the Editor, never the renderer.** `Editor/ImGuiLayer` owns the context, the GLFW platform backend and the GUI renderer (`RHIImGui::IGuiRenderer`, ImGui's Vulkan backend with dynamic rendering into any texture of one colour format, created in the `Renderer`'s `DeviceReadyCallback`, which hands the application the device and the swapchain's format once at construction). The result view's `Ui` pass hands the editor its colour target through a `UiCallback`. Neither `HedgehogRenderer` nor `RHI` has an ImGui include path or link, and the boundary check keeps it that way.
